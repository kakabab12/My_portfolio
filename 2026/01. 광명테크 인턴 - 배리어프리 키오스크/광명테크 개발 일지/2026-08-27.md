# 2026-08-27 (목) 개발일지

**미간(eyebrow.py)의 몸 밀림 문제를 근본 원인부터 찾아 고치고**, 새 실행기
`forehead.py`를 만들어 실기 테스트를 반복하며 다듬은 날.

`head.py`·`eyebrow.py`는 하루 종일 손대지 않다가, **맨 마지막에 사용자가
명시적으로 요청해서** 커서 구간만 화면 하단으로 바꿨다(14-3절).

---

## 1. 몸이 움직이면 커서도 움직이는 문제 — 근본 원인

**증상** — eyebrow.py는 8/20에 head.py에 넣은 "얼굴 기준 좌표계"(몸이
움직여도 커서가 안 밀리는 방식)의 혜택을 못 받고 있었다.

**원인** — eyebrow.py의 "미간"은 사실 `LMK_LEFT_EYE_OUTER`·
`LMK_RIGHT_EYE_OUTER`(양쪽 눈 바깥쪽 끝) **두 점의 평균**이다. 그런데 얼굴
기준 좌표계는 원점을 정확히 그 두 점의 평균으로 잡는다. 즉 "기준점 − 원점"이
**항상 정확히 0**인 계산을 하고 있었던 셈이다(같은 두 점으로 같은 식을 두
번 계산) — 그래서 이 방식을 켤 수 없었고, 예전 방식(화면 절대 픽셀)을 그대로
쓴 대가로 몸이 움직이면 커서도 밀렸다. 코드에 이미 그렇게 적혀 있었다.

## 2. 해결 — 새 실행기 `forehead.py`

기존 파일들을 건드리지 않고 새로 만들었다. 핵심은 원점과 겹치지 않는
기준점을 만드는 것.

**1차 시도 — 새 랜드마크 인덱스 추측**: 이마 쪽 랜드마크 인덱스를 하나
새로 추측해 쓰려 했으나, "새 인덱스를 추측하지 않는다"는 이 프로젝트의
기존 원칙과 어긋나 보류했다.

**최종 — 검증된 두 점만으로 혼합점을 만듦**:

```
기준점 = 눈_중점 + 비율 × (코끝 − 눈_중점)
```

새 인덱스 없이, 이미 검증된 코끝·눈 두 점만으로 원점과 다른 점을 만든다.
비율이 0보다 크기만 하면 얼굴 기준 좌표계가 정상 작동한다.

**실기 확인**
- 비율 0.25 — 몸 움직여도 커서 그대로(성공) / 고개 회전이 둔함
- 비율 0.5로 상향 — 회전 감도 양호. (이후 3절에서 다시 낮춘다)

## 3. cam on 특징점 시각화

"어디가 기준인지 다 보이게 해달라"는 요청으로, 카메라 미리보기에 원재료
전부를 그렸다 — 눈 좌/우(하늘색 점), 원점=눈 중점(마젠타 십자), 코끝(빨간
점), 원점→코끝 축(회색 선), 최종 기준점(노란 점).

**라벨 오류 발견·정정** — 이 최종 기준점을 "이마"라고 라벨링해 뒀는데,
사용자가 "미간이랑 코 사이가 왜 이마야"라고 정확히 지적했다. 코끝은 눈보다
**아래**에 있어서, 눈_중점에서 코끝 쪽으로 당긴 이 점은 이마(눈보다 위)가
아니라 콧대 부근(눈과 코 사이)에 찍힌다 — 이름이 계산과 안 맞았다. 화면
라벨과 관련 주석을 **"혼합점"**으로 정정했다(파일명·exe명은 그대로 유지 —
사용자가 범위를 그렇게 정함).

## 4. 기준점 방식 비교 — 사용자 질문에 답함

"코-눈 혼합점 vs 순수 미간, 뭐가 더 정확해?"라는 질문에 표로 정리해 답했다.
결론: **이 프로젝트 목적(배리어프리 키오스크)에는 혼합점 쪽이 더 정확하다**
— 순수 미간은 몸 밀림이라는 실사용 결함이 있고, 혼합점의 단점(입 벌림 간섭·
약간의 떨림)은 조정 가능한 부차적 문제이기 때문. 다만 비율이 최적인지는
별개 문제라고 정직하게 덧붙였다 — 바로 다음 절에서 그 비율 문제가 터진다.

## 5. 실기 버그 3건 — 근본 원인이 같았다

사용자가 실제로 써보고 세 가지를 보고했다.

1. 좌우로 커서를 움직이면 **U자 뒤집힌 포물선** 모양으로 휘어짐
2. 좌우 수평 민감도가 부족함
3. 입 벌려 클릭하려 하면 **커서가 아래로 밀림**

**①③의 원인은 하나였다** — 코끝은 얼굴 밖으로 튀어나온 3D 점이라, 고개를
돌리면 원근(패럴랙스) 때문에 순수 수평이 아니라 곡선으로 움직인다(①). 같은
이유로 입을 벌리면 코끝 랜드마크 자체가 밀리는 영향도 받는다(③). **혼합
비율(0.5)이 코 성분을 너무 많이 섞어서 생긴 부작용**이었다.

**해결** — 비율을 낮추고(①③ 완화), 감도는 별도로 올려서(②) 세 요청이
서로 상쇄되지 않게 했다.

```
FOREHEAD_NOSE_BLEND_RATIO   0.5  → 0.3
SENSITIVITY_X_OVERRIDE      1.124 → 2.0
```

사용자 확인: "좋다 다 해결됐어."

## 6. 저조도(어두운 곳) 인식 문제

다음 보고: "미간(eyebrow.py)은 불 꺼도 인식됐는데 이번 것(코 성분 섞인
혼합점)은 어두우면 바로 인식이 안 되네."

**원인은 이미 8/20에 실측된 것과 같았다** — 코끝(랜드마크 1개)은 매끈하고
무늬 없는 면이라 어두우면 모델이 위치를 못 잡고 흔들리는데, 미간(두 눈
바깥쪽 끝의 평균)은 눈꼬리 명암이 뚜렷해 어두워도 잘 잡힌다(그때 실측: 어두울
때 코 1.83배 흔들림 vs 미간 1.15배). 혼합점이 코 성분을 30% 섞고 있으니 그
불안정성도 그만큼 물려받고 있었다.

**1차 조치** — head.py가 이미 검증해 둔 방법(`NOSE_CLUSTER_AVERAGING`,
코끝 한 점 대신 코 아래쪽 여러 점의 평균)을 그대로 가져왔다. 서로 무관한
흔들림이 점 개수만큼 상쇄된다.

## 7. CLAHE 적용 — 논문 조사 요청

"조도 문제를 완화할만한 기술이나 논문 없나 찾아서 적용해줘" 요청으로
**CLAHE**(Contrast Limited Adaptive Histogram Equalization, Zuiderveld,
Graphics Gems IV, 1994)를 적용했다. 저조도 얼굴 인식 전처리의 표준 기법 —
화면을 작은 타일로 나눠 국소적으로, 대비 상한을 두고 명암을 편다(잡음
폭주 방지). OpenCV에 이미 내장돼 있어 새 의존성 없음.

**설계**
- 밝을 때는 아예 건드리지 않음(원본 그대로) — 이미 잘 보이는 영상에 대비를
  더 올리면 부작용만 생길 위험
- 인식용 프레임에만 적용, 화면에 보여주는 미리보기는 원본 그대로 — 사용자가
  보는 색감은 안 바뀌고 인식만 좋아짐
- Y(밝기) 채널에만 적용, 색(Cr·Cb)은 그대로 — 색 얼룩 방지

**성능 최적화** — 처음 버전은 밝기 판정 자체가 실측 5ms 들었다(1280x720
색공간 변환 비용). 32×32 축소 썸네일로 먼저 밝은지만 확인하는 방식으로
바꾸니, 밝을 때(대부분의 시간) **0.016ms — 사실상 공짜**가 됐고 실제로
어두울 때만 전체 처리 비용(~8ms)을 낸다. 8/20 `cv2.pollKey()` 최적화와
같은 원리 — "대부분의 경우엔 안 낸다."

**실기 확인**: "일단 어두운데서도인식 잘된다" — 실제 발급기 화면(FINOK
9:16 키오스크)에서 스크린샷으로 확인.

## 11. 우수조달 대비 — 국제표준 성능 측정 체계 구축

"모든 기술 총동원해서 우수조달 1등 할 만큼" 요청. 다만 새 기능을 잔뜩 넣는
것보다 **심사에서 실제로 점수가 되는 것**에 집중하는 게 맞다고 판단했다.

### ISO 9241-411 처리량 측정 (핵심)

기존 `measure_accuracy.py`는 성공률·시간·최소 버튼 크기를 재는데, 이건
**다른 입력장치와 견줄 공통 잣대가 아니다.** "성공률 90%"라고 해도 심사위원은
마우스보다 나은지 알 수 없다.

ISO 9241-411은 마우스·터치·시선추적을 같은 숫자 하나로 비교하도록 국제적으로
합의된 절차이고, 그게 **처리량(bit/s)** 이다. 원문 확인 후 구현했다:

```
TP = IDe / MT,  IDe = log2(Ae/We + 1),  We = 4.133 x SD(dx)
```

`4.133`은 정규분포 +-2.066 표준편차(전체의 96%)다. 편차 dx는 MacKenzie의
표준 사영식으로 구한다.

**이 표준이 좋은 이유** — "대충 빨리 찍기"로 점수를 못 올린다. 산포가 커지면
We가 커져 IDe가 깎이며 자동 상쇄된다. 실제로 검증했다:

```
신중: SD 10.7px -> IDe 1.706 / 1.00초 -> TP 1.706
대충: SD 21.4px -> IDe 1.092 / 0.50초 -> TP 2.184
      시간을 절반으로 줄여도 난이도가 0.614 bit 깎여 보정됨
```

수식은 전부 손계산과 소수점까지 대조했다 — 사영 편차 4케이스, 처리량,
Fitts 회귀 계수 복원까지.

비교 기준값도 확보했다(같은 표준으로 측정된 공개 문헌):
마우스 2.75 / **머리 조작 2.04** / 시선 조작 1.85 bit/s.

> ⚠ 계측 도구는 완성·검증됐지만 **실측값은 아직 없다** — 사람이 직접 시험해야
> 나온다. 제출 전 반드시 측정해야 한다.

### 거리 적응 평활 — 자체 실측을 알고리즘으로

8/26에 재둔 값을 다시 보다가 발견했다:

```
안구간거리 90px x 흔들림 2.0px = 180
           60px x        3.0px = 180
           40px x        4.5px = 180
```

**곱이 정확히 일정** — 흔들림이 1/거리에 정비례한다. 당연한 결과였다. 커서를
`(랜드마크 이동 px / 안구간거리)`로 정하는데 랜드마크 잡음은 거리와 무관하게
일정하니, 나누는 값이 작아질수록 그대로 증폭된다.

그래서 평활 강도를 거리에 비례시켜 상쇄했다. 결과:

| 안구간거리 | 이전 | 이후 |
|---|---|---|
| 90px (가까움) | 17.4px | 17.4px (동일) |
| 60px (기준) | 26.1px | 26.1px (동일) |
| 40px | 39.1px | **31.8px (18.6% 개선)** |
| 30px | 52.1px | **36.1px (30.6% 개선)** |

**중간에 한 번 되돌렸다.** 처음엔 배율 상한을 2.0으로 뒀는데, 시뮬레이션에서
가까운 사용자(90px)가 **오히려 21% 더 떨렸다**. 반응성을 얻는 대신 이미
검증해 둔 감각을 깨는 건 손해다 — 상한을 1.0으로 묶어 "같거나 나아지기만
한다"를 보장하게 바꿨다.

## 12. 실기 요청 3건 — 포물선·60fps·떨림

"포물선 해결했지? 아직 성에 안 차. 60fps처럼 나오게. 떨림도 완벽하게."

### 12-1. 포물선 — "해결"이 아니라 "완화"였다고 정정

5절에서 코 비율을 0.5 -> 0.3으로 낮춰 사용자가 "다 해결됐어"라고 했지만,
다시 물었을 때 **정직하게 정정했다**. 곡률을 40% 줄인 것이지 없앤 게 아니고,
남은 30%만큼은 그대로 휜다.

**원인을 제대로 짚었다** — 커서 기준점에 섞인 코는 얼굴 밖으로 튀어나온
3차원 점이다. 고개를 좌우로 돌리면 코끝이 카메라에서 멀어졌다 가까워지며
투영 배율이 바뀌어 **세로 위치까지 같이 밀린다**. 그 밀림은 가로 회전량의
**제곱에 비례**한다 — 즉 궤적이 정확히 2차 곡선이다.

그러면 같은 형태를 빼면 원리적으로 상쇄된다:

```
보정 후 세로 = 세로 + 계수 x (가로offset)^2
```

**계수는 0.0(보정 없음)으로 뒀다.** 정확한 값은 카메라 화각·설치 각도·얼굴
형태에 따라 달라서 추측으로 넣으면 안 된다. 대신 실측 도구를 만들었다 —
`scripts/measure_arc.py`. 고개를 좌우로 왕복하면 커서 궤적에 2차 곡선을
맞춰(최소제곱) 넣을 계수를 알려준다. 계수 복원·보정 효과 모두 검증했다.

### 12-2. 렌더 30 -> 60fps

먼저 **30으로 묶어둔 근거를 다시 읽었다.** 세 가지가 적혀 있었는데 그중
①번이 이 구조에서는 **틀렸다**:

> ① "얼굴 인식이 카메라 속도(30fps)로 들어오니 더 자주 그려도 새 정보가 없다"

렌더 루프는 같은 좌표를 다시 그리는 게 아니라 목표를 향해 **보간(lerp)**
한다. 추론과 추론 사이에도 매 틱 새로운 중간 위치가 만들어지므로, 두 배로
그리면 그 궤적이 두 배로 촘촘해진다.

③번(예산)은 실측으로 확인했다:

```
커서 영역 지우기  0.001ms
커서 그리기       0.172ms
합계             약 0.17ms   vs   60fps 예산 16.7ms  (여유 100배 가까움)
```

**★함정 하나를 발견해서 같이 막았다** — 그냥 60으로 올리면 보간 계수가
렌더 주기에 묶여 있어서 **같은 alpha가 두 배 자주 적용된다.** 커서가 두 배
빨리 목표에 붙어, 그동안 실기로 맞춰 온 손맛(0.35->0.6->0.45->0.38 이력)이
통째로 어긋난다.

보간 계수의 시간 기준을 렌더 속도와 분리했다(`LERP_REFERENCE_FPS = 30`).
검증 결과:

```
기준 분리함  : 30fps vs 60fps 궤적 차이  1.1e-16  (부동소수점 한계)
기준 분리안함:                          255.6px  (손맛 완전히 바뀜)
```

즉 **"손맛은 그대로, 화면만 매끄럽게"** 가 성립한다.

> 중간에 검증 테스트를 한 번 잘못 짰다. 0.05초에는 30fps 표본이 없는데
> 가장 가까운 0.0667초와 비교해 "차이 있음"으로 나왔다. 두 쪽 모두 표본이
> 있는 시각(1/30 배수)에서만 비교하도록 고쳐서 확인했다.

### 12-3. 1€ 필터 재튜닝 — 반쪽만 켜져 있었다

**`beta = 0.0`은 속도 적응을 꺼버리는 값이었다.** 1€ 필터를 도입해 놓고
정작 핵심 기능을 안 쓰고 고정 저역통과 필터처럼 굴리고 있었던 셈이다
(8/27 오전에 "논문 권장 시작값"이라며 그대로 둔 게 화근이었다).

논문의 표준 튜닝 절차대로 조합을 훑었다:
① beta=0으로 두고 정지 떨림이 잡힐 때까지 min_cutoff를 낮춘다
② 그 다음 지연이 사라질 때까지 beta를 올린다

| min_cutoff / beta | 정지 떨림 | 느린 조준 지연 | 빠른 이동 지연 |
|---|---|---|---|
| 1.00 / 0.0 (기존) | 0.89px | 30.49px | 274.40px |
| **0.25 / 1.5 (채택)** | **0.68px** | **21.60px** | **61.41px** |
| | **−24%** | **−29%** | **−78%** |

**절충이 아니라 세 지표 전부 개선**이다. beta가 지연을 압도적으로 줄이면서
떨림 비용은 거의 없기 때문이다 — 움직일 때만 평활이 풀리므로. 그래서
min_cutoff는 더 낮춰 정지 떨림을 잡고, beta를 올려 추종을 되살리는 조합이
동시에 성립한다.

### 12-4. 테스트 17건으로 확대

`tests/test_cursor_smoothing.py`에 곡률 보정·렌더 기준 분리 검사를 추가했다.

**테스트를 세 번 고쳐 썼다** — 처음엔 계수를 추측해 넣어 실패했고, 유도식으로
바꿔도 실패했다. 원인을 파보니 두 가지였다:
- 훑는 폭이 너무 커서 **커서가 화면 밖으로 포화**돼 곡률이 평평해져 있었다
- **캘리브레이션이 훑는 도중에 잡혀** 중심이 한쪽으로 밀려 있었다
- 마지막으로, 움직이면서 재니 **EMA 지연** 때문에 커서가 목표에 못 미친 값이
  잡혀 계수가 3.6배 과대 추정됐다

각 위치에서 수렴할 때까지 머물게 하고 폭을 줄이니 통과했다. 검증 도구 자체가
틀리면 검증이 무의미하다는 걸 다시 겪었다.

## 13. 커서 조작 영역을 화면 아래쪽으로 반전

"키오스크 지금 위쪽 부분만 되는데 반전으로 밑쪽 부분만 조작되게 해달라."

실제 키오스크에서는 사용자가 화면 아래쪽을 주로 조작한다 — 휠체어를 타거나
키가 작은 사용자에게도 아래쪽이 닿기 쉽다. 그런데 지금은 커서가 화면 위쪽
70% 구간에만 들어가고 아래 30%는 아예 못 간다.

### 고치면서 구조를 정리했다

원래는 `* TOP_HALF_Y_SCALE`이 **코드 11곳에 흩어져** 있었다. 커서 이동,
목표 좌표, 시작 위치, 안내 문구 위치, 고장 알림 위치, 로그 메시지까지 —
한 곳만 빠뜨리면 **커서와 안내 문구가 서로 다른 자리에 놓이는** 구조였다.

그래서 값을 흩뿌리는 대신 **매핑 함수 하나로 묶었다**:

```python
CURSOR_Y_SPAN = 0.7              # 화면 세로 중 커서가 쓰는 폭
CURSOR_Y_ANCHOR_BOTTOM = True    # True=아래쪽, False=위쪽(예전 동작)

def _cursor_y_to_screen(cursor_y_ratio):
    return CURSOR_Y_OFFSET + cursor_y_ratio * CURSOR_Y_SPAN
```

이제 위/아래 전환이 **스위치 하나**로 끝나고, 전체 화면을 쓰려면 SPAN을
1.0으로 올리면 된다.

### 검증 (1080px 화면 기준)

| 트래커 세로좌표 | 화면 위치 |
|---|---|
| 0.00 (맨 위) | 324px |
| 0.50 (중앙) | 702px |
| 1.00 (맨 아래) | **1080px — 화면 바닥에 닿음** |

커서 도달 구간 324~1080px = 화면 아래쪽 70%. 의도대로다.

### 함께 고친 것 — 계측 스크립트 2개

`measure_arc.py`와 `measure_throughput_iso.py`가 이 상수를 가져다 쓰고
있었다. 안 고치면 **과녁이 커서가 닿지 않는 위쪽에 그려져** 측정 자체가
불가능해진다. 두 스크립트도 매핑 함수를 쓰도록 맞췄고, ISO 시험 창은
커서 구간에 겹치도록 띄우는 위치까지 옮겼다.

> 이번 변경 파일은 `forehead.py` + 계측 스크립트 2개, 총 3개다.
> `head.py`·`eyebrow.py`는 오늘 하루 종일 그대로다(수정시각 8/26 17:47).

## 14. 실기 재보고 3건 — 바닥 미도달·포물선 잔존·감도

13절에서 커서를 하단으로 옮긴 뒤 바로 재보고가 왔다.

### 14-1. "화면 밑 끝까지 안 닿아" — 감도가 아니라 기하학적 한계였다

처음엔 단순 감도 문제로 보였는데, 계산해 보니 **물리적으로 못 닿는** 상태였다.

커서가 화면 끝에 닿으려면 `dy x 감도`가 클램프값(config `max_offset_ratio`
= 0.5)에 도달해야 한다. 그런데 혼합점은 코를 **30%만** 섞으므로 세로로
튀어나온 양이 아주 작다 — 고개를 45도 숙여도 신호가 0.5에 한참 못 미친다.

어림 계산: 감도 2.0에서 한계가 화면의 **약 84%**. 실제 보고("밑 끝까지 안
닿아")와 정확히 맞았다. 검증으로 확인:

```
감도 2.0  ->  화면 903px 에서 멈춤 (바닥 미도달)
감도 3.8  ->  화면 1080px 도달      (바닥)
```

세로 2.0 -> **3.8**, 가로 2.2 -> **2.8**로 올렸다. 감도를 올리면 잡음도
증폭되지만, 12-3에서 1€ 필터를 제대로 튜닝해 둔 덕(정지 떨림 -24%)에
예전 감도 때보다 여유가 있다.

### 14-2. 포물선이 여전함 — 값을 넣었다

12-1에서 보정 구조는 만들었지만 계수를 **0.0(보정 없음)** 으로 두고 실측을
부탁했었다. 실기에서 여전히 휜다고 해서 값을 넣었다.

**부호는 관측으로 정해졌다** — "U 반대(∩)"라고 했으므로 양끝이 위로 솟는
것이고, 양수를 넣어 아래로 눌러 편다. `ARC_COMPENSATION = 1.0`.

> ⚠ 크기는 얼굴 치수·화각으로 어림한 값이지 **실측이 아니다.** 주석에 조정
> 방향을 적어 뒀다 — 아직 ∩이면 올리고, ∪로 뒤집히면(과보정) 낮춘다.
> `scripts/measure_arc.py`를 한 번 돌리면 정확한 값이 나온다.

### 14-3. head.py·eyebrow.py도 하단으로 (요청)

하루 종일 보호해 온 두 파일을, **사용자가 명시적으로 요청**해서 바꿨다.

13절에서 forehead.py에 만든 구조(SPAN + ANCHOR + 매핑 함수)를 그대로
적용했다. **폭(0.5)은 그대로 두고 붙는 쪽만 뒤집어** 지금까지 실기로 맞춰
온 조작 감각은 유지했다.

| 파일 | 폭 | 커서 도달 구간 (1080px 기준) |
|---|---|---|
| head.py | 0.5 | 540 ~ **1080px** |
| eyebrow.py | 0.5 | 540 ~ **1080px** |
| forehead.py | 0.7 | 324 ~ **1080px** |

### 14-4. 같이 발견해서 고친 것 2가지

**① `measure_accuracy.py`의 과녁 위치** — 이 스크립트는 창이 전체화면이라
캔버스 y가 곧 화면 y인데, 과녁을 `y_ratio * 구간높이`로만 그리고 있었다.
커서 구간이 하단으로 옮겨졌으므로 **시작점을 안 더하면 커서가 닿지 않는
위쪽에 과녁이 그려져** 측정 자체가 불가능해진다. 오프셋을 더하도록 고쳤다.

**② 빌드 스크립트 4개의 cp949 줄표 크래시** — head/eyebrow exe 빌드가
실패하길래 봤더니, **8/25에 트래커 본체에서 고쳤던 바로 그 버그**가 빌드
스크립트에는 그대로 남아 있었다(오늘 아침 forehead 것만 고쳤음).

```
UnicodeEncodeError: 'cp949' codec can't encode character '—'
```

exe는 이미 다 만들어진 뒤 마지막 출력 줄에서만 죽어 결과물엔 영향이
없었지만, "빌드 실패"로 보이니 고쳤다. dpad·dpad_overlay 것까지 4개 전부.

> 공교롭게도 **이 작업을 하던 내 변환 스크립트에서도 같은 줄표 크래시가
> 났다.** 한 파일은 쓰이고 다른 파일은 안 쓰인 채로 중단돼서, 상태를
> 확인하고 나머지만 다시 처리해야 했다. 같은 함정에 세 번째 걸린 셈이다.

## 15. 곡률 과보정 되돌림 + 카메라 자동 협상 신설

### 15-1. 다시 원점으로 — 어림값을 반복하지 않기로 함

14-2에서 넣은 어림값(`ARC_COMPENSATION = 1.0`)을 실기에서 재확인해보니
"여전히 U 반대(∩)로 커서가 움직인다"는 보고가 왔다.

원인은 두 가지가 겹친 것이었다. ① 그 계수 자체가 실측이 아니라 어림값이었고,
② 같은 커밋에서 가로 감도를 2.2→2.8로 올려 `offset_x`가 훨씬 쉽게 클램프
(0.5)에 닿게 됐다. 보정식이 `offset_x²`라서 클램프 근처에서 밀림량이
급격히 커지고, 제곱이라 **부호가 사라져 좌우 어느 쪽으로 돌려도 항상
아래로만** 밀렸다 — "좌우 이동하면 다 밑으로 하강"이라는 재보고와 정확히
일치했다.

검증 안 된 값을 넣은 게 실제로 새 문제를 만들었다. **이번엔 세 번째
추측을 하지 않고** `ARC_COMPENSATION`을 0.0으로 되돌렸다. 계수는 카메라
화각·설치 각도·얼굴 형태에 따라 달라 실측 없인 알 수 없는 값이라는 걸
두 번의 실패로 다시 확인한 셈이다 — 도구(`measure_arc.py`)는 이미 만들어
검증까지 끝났으니, 이번엔 그걸로 실제로 재는 것 말고는 답이 없다.

### 15-2. 카메라 자동 협상 신설

"MSMF + MJPG + 1280x720 이거 아니여도 모든 카메라 장치값을 받을 수 있게
해줘" 요청. 계기는 연구실에서 로지텍 카메라(0번)로 `eyebrow.exe`를 실행하니
카메라가 안 켜진 것 — **팀장님이 만든 다른 프로그램은 같은 0번을 잘 여는
걸로 봐서 카메라 자체 문제가 아니라 이 프로젝트가 조합 하나만 고정해서
여는 게 문제**였다.

**설계에서 가장 신경 쓴 것 — 안전.** 8/26에 이미 실측으로 확인해 둔 사실이
있다: MSMF는 문제 있는 조합을 열 때 파이썬 예외가 아니라 **프로세스 자체를
죽이는 크래시**를 낸다. 그래서 `camera_check.py`의 진단 기능도 조합마다
자식 프로세스를 따로 띄운다. 만약 이번 자동 협상을 트래커 본 프로세스
안에서 여러 조합을 직접 시도하는 식으로 만들었다면, 그중 하나가 크래시를
내는 순간 **헤드트래커 전체가 아무 예고 없이 죽는다** — "카메라가 안
켜진다"보다 훨씬 나쁜 결과였을 것이다.

그래서 새로 만들지 않고 **이미 검증된 격리 방식을 그대로 재사용**했다.
`camera_check.py --try-combo`를 자식 프로세스로 불러 결과를 받는 프로토콜
그대로다.

**비용 설계** — 기본 설정으로 잘 열리는 절대다수 경우엔 새 모듈을 아예
안 건드린다. `camera_stream.init_camera`가 원래 하던 대로 한 번 여는 데
성공하면 그걸로 끝나고, **실패했을 때만** 협상이 시작된다:

```
1차: 설정된 조합으로 그냥 열어본다 (예전과 완전히 동일, 추가 비용 0)
  실패 시 ->
2차: 자식 프로세스로 조합 7가지를 순서대로 시험(첫 성공에서 멈춤)
  성공 시 -> config를 그 조합으로 갱신하고 본 프로세스에서 다시 연다
```

`head.py`·`eyebrow.py`·`forehead.py`·`main_dpad.py` 네 실행기 모두에
연결했다 — `config_path`를 안 넘기는 기존 호출부(camera_probe 등)는 예전과
동일하게 동작한다.

**만들면서 발견해서 고친 것** — 내가 처음 넣은 타임아웃(20초)이
`camera_check.py` 자체가 쓰는 값(40초)보다 짧았다. 이 프로젝트가 8월 초에
실측한 대로 정상 장치도 MSMF 오픈에 11초 넘게 걸리는 경우가 있는데, 20초로는
그 여유(오픈 15초 + 표본 촬영)를 못 채워 **정상인데 느린 카메라를 실패로
오판**할 뻔했다. 이미 검증된 값(40초)을 그대로 가져다 쓰는 것으로 고쳤다.

**테스트 12건** — 실제 카메라·자식 프로세스 없이 mock으로 검증했다.
가장 중요한 건 "기본 설정으로 잘 열리면 협상 모듈을 아예 안 건드리는가"
(성공 케이스의 비용이 조금도 늘면 안 되므로), 그리고 "제일 먼저 성공하는
조합에서 멈추고 나머지는 안 도는가"다.

## 오늘의 교훈

같은 원인(코끝의 원근 특성)이 몸-밀림 문제 해결책이면서 동시에 새 부작용
(포물선·입벌림 밀림·저조도 불안정)의 근원이었다 — 하나를 고치려고 들여온
재료가 다른 문제를 만들 수 있다는 걸 하루 안에 반복해서 겪었다. 그때마다
"코 성분을 얼마나 섞을지"라는 단일 손잡이(비율)로 되돌아와 절충했다.
그리고 이미 확보된 원칙("새 랜드마크 인덱스를 추측하지 않는다", "저조도엔
점 여러 개 평균")을 어기지 않고도 문제를 풀 방법이 매번 있었다 — 새로
만들기 전에 이미 검증된 것부터 다시 살펴보는 습관이 이번에도 유효했다.

라이선스 건도 비슷했다 — "스택 전체를 검토했다"는 문서가 있어도, 실제로
코드가 뭘 가져다 쓰는지 다시 확인하기 전까지는 그 문서가 맞는지 알 수
없었다. 새로 뭘 추가할 때뿐 아니라, "이미 정리해 둔 것"도 가끔 원본과
맞춰 다시 봐야 한다.

**"해결했다"고 말한 것이 사실은 "완화"였던 게 오늘 두 번 있었다.** 포물선
(12-1)과 1€ 필터(12-3)다. 특히 필터는 "논문 권장 시작값"이라며 넣어 둔
`beta=0`이 정작 그 논문의 핵심 기능을 꺼버리는 값이었다 — 출처를 인용해
놓고 내용을 안 쓴 셈이다. 남이 물어보지 않았으면 그대로 갔을 것들이라,
**"됐다"고 말하기 전에 한 번 더 재보는 게 맞다.**

그리고 검증 도구를 세 번 고쳐 썼다(12-4). 포화·캘리브레이션 오염·EMA 지연
때문에 계속 틀린 답이 나왔는데, 그때마다 코드를 의심하기 전에 **테스트가
맞는지부터** 확인한 게 옳았다. 검증 도구가 틀리면 검증 자체가 무의미하다.

마지막으로 — **cp949 줄표(—) 크래시에 오늘 하루 세 번 걸렸다.** 8/25에
트래커 본체에서 고쳤던 버그인데, 빌드 스크립트 4개에 그대로 남아 있었고
(14-4), 심지어 그걸 고치려고 짠 내 변환 스크립트에서도 같은 게 터졌다.
한 곳을 고쳤다고 그 부류가 끝난 게 아니다 — **같은 원인을 공유하는 자리를
그때 함께 훑었어야** 했다.

그리고 **곡률 계수를 두 번 추측하고 두 번 다 되돌렸다**(12-1, 15-1).
0.0(무보정) -> 1.0(어림) -> 0.0(재복귀). 첫 번째 추측이 실패했으면 거기서
"그럼 다른 값"으로 넘어가지 말고 바로 실측 도구를 썼어야 했다 — 이미
만들어서 검증까지 끝낸 도구를 두고 어림짐작을 반복한 건, 도구를 만든
보람을 스스로 깎아먹은 것이다.

반대로 카메라 자동 협상(15-2)은 처음부터 **추측하지 않는 방식**으로
설계했다 — 이미 검증된 조합 목록과 격리 방식을 그대로 가져다 썼다.
안 되면 사람이 진단 도구를 돌리게 하는 대신, 그 도구가 이미 증명한
안전한 절차를 트래커 스스로 밟게 만든 것 — 오늘 두 번 겪은 실패와
정반대로 접근해서 나온 결과다.
