## 1. 컴파일도 되고 시험도 통과하는데 실행하면 죽는 것 — 둘

같은 모양의 실수가 더 있는지 pyflakes(정의 안 된 이름을 찾는 도구)로 전 파일을 훑었습니다.

`make_head_exe.bat`·`make_eyebrow_exe.bat`·`make_forehead_exe.bat` 등이 부르는 파이썬 7개가
전부 이렇게 시작했습니다.

    import os
    import sys

실행하자마자 `NameError: name 'sys' is not defined`입니다. `pipe_listen.py`(델파이 대역)도
같았습니다.

저장소 이력을 따라가 보니 **8/28 저녁 "cp949 인코딩 버그 구조적 차단" 커밋**에서 들어왔습니다.
14개 파일에 공용 함수를 일괄로 넣으면서 경로 줄을 import 위에 끼워 넣은 것입니다. 같은 날
오후 판은 멀쩡했습니다. 그 뒤로 이 도우미들은 한 번도 성공할 수 없었는데, 9/9~10의 화면비
exe 6개는 **다른 빌드 도우미**를 써서 아무도 눈치채지 못했습니다.

**버그를 구조적으로 막으려던 일괄 수정이 다른 버그를 만든 것**입니다. 고친 파일을 하나씩

## 4. 지운 기법 다섯

사용자 요청("필요없는 기법들은 다 없애자")으로, 기법마다 **지금 켜져 있는지, 켜져 있다면
실제로 무언가를 하는지, 측정 결과가 어땠는지**를 확인하고 지웠습니다.

| 기법 | 지운 이유 |
|---|---|
| 곡률 자동 보정(`auto_arc`) | 9/11 재측정 — 실사용을 흉내 낸 2분 뒤 **30가지 조건 모두** 좌우 움직임의 세로 휨이 커졌다(2~5% → 14~15%). 9/24 끄기로 결정하고 코드에서도 지움 |
| 렌즈 배럴 왜곡 되돌리기(k1) | 정규 얼굴이면 휨 절반, 얼굴이 다르면 **다섯 배 악화**. 가려낼 방법이 없어 9/3부터 꺼 둔 채였다 |
| 머리 자세 각도 매핑 | forehead.py 주석에 "**실제로 커서를 이 방식으로 움직여 본 적은 없다**". 상대 회전 매핑이 같은 문제를 푼다 |
| 입 오므리기 재정렬 | 오탐 때문에 7/30에 껐고 응시 재정렬로 대체됐다 |
| 조절 창의 감도·곡률 슬라이더 | 세 트래커가 상대 회전 매핑으로 바뀐 뒤 이 값은 **쓰이지 않는다.** 연구실 `eyebrow_tuning.json`에 곡률 −1.008이 저장돼 있었다 — 누군가 효과 없는 손잡이를 맞추느라 애쓴 흔적 |

조절 창을 고치다 **안내 문구가 "가로 각도" 슬라이더와 같은 줄에 겹쳐 그려지던 것**도 찾아
고쳤습니다(위젯 겹침 시험 추가).

**남긴 것**(측정으로 효과가 확인된 것): 고개 회전 방식(4~6배), 렌즈 자가 보정(3~7배), 1유로
필터(떨림 −31%), 클릭 붙잡기(드래그 방지), 거리 조절(옮긴 뒤 오차 13.4% → 0.5~2.5%), 목
가동범위 배려(41 → 90%), 응시 클릭.

**미룬 것 — 옛 2D 커서 방식.** 회전 방식의 캘리브레이션이 실패할 때만 타는 비상 경로라
실제로는 거의 안 탑니다. 지우면 세 파일의 감도·곡률 계수·점 평활 등 수백 줄과 시험 여럿을

## 5. 시험이 다른 파이썬으로 돌고 있었다

exe들은 `py -3.11 head.py`처럼 폴더의 소스를 실행하는 얇은 실행기입니다. 그러니 오늘 고친
것은 exe를 다시 빌드하지 않아도 반영됩니다. 그런데 **제품은 파이썬 3.11로 도는데 시험은
3.13으로** 돌고 있었습니다.

| | 키오스크(`install.bat` → `requirements.txt`) | 이 PC의 3.11 | 시험을 돌리던 것 |
|---|---|---|---|
| 파이썬 | 3.11.5 | 3.11.5 | 3.13 |
| numpy | **1.26.4** | 2.2.6 | 2.4.4 |
| OpenCV | **4.10** | 5.0 | 5.0 |
| MediaPipe | 0.10.14 | 0.10.14 | 0.10.35 |

3.12부터 허용된 문법이 섞였으면 3.11에서는 **실행 자체가 안 됩니다.** 3.11로 전 파일을
컴파일했고(0건), numpy 2 전용 기능도 찾았습니다(0건). 그리고 E: 드라이브에 **키오스크와 같은
조합의 가상환경**을 만들어 시험 전체·스모크·장시간 실행을 다시 돌렸습니다
(E:/작업/_출시검증_py311, 프로젝트 폴더와 시스템 파이썬은 안 건드림).

### 옛 고정 버전(OpenCV 4.10)에서 렌즈 보정이 백 배 넘게 느렸다

그 환경에서 스모크 6가지와 12분 장시간 실행 3번은 통과했습니다. 그런데 **시험 전체가 29분이
지나도 끝나지 않았습니다.** 좁혀 보니 렌즈 자가 보정의 `cv2.calibrateCamera` 한 번이었습니다.
입력을 똑같이 두고(가상 카메라 얼굴 22점 × 60뷰) 설치 조합만 바꿔 측정했습니다
(`데이터 수치/lens_speed.py` → `렌즈보정_속도.csv`).

| 설치 조합 | 한 번 걸린 시간 (3회) | 결과 초점거리 / k1 / 재투영오차 |
|---|---|---|
| numpy 1.26.4 + OpenCV 4.10 (옛 고정) | **20.4~20.9초** | 435.4 / −0.142 / 0.462 |
| numpy 2.2.6 + OpenCV 5.0 (이 PC의 3.11) | 0.10~0.22초 | 435.4 / −0.142 / 0.462 |

## 6. 장시간 실행 — 무인 키오스크니까

키오스크는 사람이 없는 동안에도 켜져 있습니다. 스모크 흐름을 되풀이하며 메모리와 스레드 수가
늘어나는지 봤습니다.

**옛 고정 버전(4.10) 환경, 12분 × 3** — 세 트래커 모두 통과(클릭 59·드래그 20·누름 79 = 뗌 79,
ERROR 0, 스레드 6개 고정). 처음에는 스레드 수가 "2~6개"로 실패였는데, 종료한 뒤의 표본이 섞인
**실행기 쪽 잘못**이었습니다(표본을 종료 전으로 제한). 메모리 증가 기울기는 실행마다
−23~+30MB/시간으로 들쭉날쭉해 경향이 없었습니다.

**새 고정 버전(5.0) 환경, 30분 × 3 (9:16 키오스크)**

| | head | eyebrow | forehead |
|---|---|---|---|
| 정상 종료, 로그 ERROR | 0건 | 0건 | 0건 |
| 클릭 / 드래그 | 149 / 50 | 149 / 50 | 149 / 50 |
| 누름 = 뗌, 끝에 눌린 채 아님 | 199 = 199 | 199 = 199 | 199 = 199 |
| 메모리 (시작 → 끝) | 108 → 109MB | 109 → 109MB | 109 → 110MB |
| 스레드 수 | 6개 고정 | 6개 고정 | 6개 고정 |
| 커서 위치 확인 3개(좌우 방향·얼굴 복귀·옆 사람) | 통과 | 통과 | **값 없음(-)** |

**forehead의 빈 값은 아직 원인을 모릅니다.** 틀린 위치가 나온 것이 아니라 값 자체가 비었습니다.
그래서 커서가 엉뚱하게 움직였다는 증거는 아니지만, 확인하기 전에는 통과로 치지 않습니다. 같은
forehead로 돌린 40초 스모크 2가지(두 화면비)는 통과했습니다. 사용자 요청("일단 깃허브에
올려줘")으로 원인 확인보다 올리기를 먼저 했고, 커밋 메시지에도 그대로 적었습니다.
