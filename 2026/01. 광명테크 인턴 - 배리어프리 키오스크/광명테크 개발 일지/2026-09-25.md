## 1. 컴파일도 되고 시험도 통과하는데 실행하면 죽는 것 — 둘

9/10에 리팩터가 `main()` 안쪽 정의를 지웠을 때 컴파일·자가 점검·테스트가 전부 통과했습니다.
같은 모양의 실수가 더 있는지 pyflakes(정의 안 된 이름을 찾는 도구)로 전 파일을 훑었습니다.

### 빌드 도우미 6개 — 한 달 가까이 아무도 exe를 못 만들었다

`make_head_exe.bat`·`make_eyebrow_exe.bat`·`make_forehead_exe.bat` 등이 부르는 빌드 도우미 6개가
전부 이렇게 시작했습니다.

    """설명"""
    sys.path.insert(0, os.path.dirname(...))    ← sys, os를 아직 안 불렀다
    import os
    import sys

실행하자마자 `NameError: name 'sys' is not defined`입니다. `pipe_listen.py`(델파이 대역)도
같았습니다.

저장소 이력을 따라가 보니 **8/28 저녁 "cp949 인코딩 버그 구조적 차단" 커밋**에서 들어왔습니다.
14개 파일에 공용 함수를 일괄로 넣으면서 경로 줄을 import 위에 끼워 넣은 것입니다. 같은 날
오후 판은 멀쩡했습니다. 그 뒤로 이 도우미들은 한 번도 성공할 수 없었는데, 9/9~10의 화면비
exe 6개는 **다른 빌드 도우미**를 써서 아무도 눈치채지 못했습니다.

**버그를 구조적으로 막으려던 일괄 수정이 다른 버그를 만든 것**입니다. 고친 파일을 하나씩
실제로 돌려 봤다면 바로 보였을 것입니다.

### 좌우 반전 점검 도구 — 안내대로 정확히 움직인 사람만 죽는다

`scripts/check_direction.py`는 9/10에 "오른쪽·왼쪽을 따로 측정해 서로 반대인지 확인"하도록

경로 줄은 import 뒤로 옮기고 남은 두 줄은 지웠습니다. 그리고 `tests/test_script_names.py`를

## 3. 세 트래커를 처음부터 끝까지 돌려 보는 실행기

테스트 800여 개는 판정·매핑 모듈을 따로 봅니다. 세 트래커의 `main()`은 거의 아무도 안
거칩니다. 그래서 `tests/tracker_smoke.py`를 만들었습니다.

**가짜로 바꾸는 것은 사용자 화면·마우스·파일을 건드리는 것뿐입니다** — 실제 마우스(기록만
함), 시스템 커서 숨기기, 카메라(검은 프레임), 얼굴 인식 모델(가상 카메라 얼굴을 실제 인식
결과와 같은 모양으로 감쌈), 전체 화면 창, 로그 파일, 콘솔 입력. 전처리·얼굴 앵커·커서
계산·입 판정·클릭 붙잡기·렌더 루프·스레드·종료 절차는 **진짜 코드가 돕니다.**

가상 사용자는 38초 동안 이렇게 씁니다 — 안내대로 가운데를 보며 대기 → 오른쪽을 가리키고
클릭 → 왼쪽 위를 가리키고 클릭 → 드래그 → **얼굴이 2초 사라짐** → 다시 나타나 안내대로

## 4. 지운 기법 다섯

사용자 요청("필요없는 기법들은 다 없애자")으로, 기법마다 **지금 켜져 있는지, 켜져 있다면
실제로 무언가를 하는지, 측정 결과가 어땠는지**를 확인하고 지웠습니다.

| 기법 | 지운 이유 |
|---|---|
| 곡률 자동 보정(`auto_arc`) | 9/11 재측정 — 실사용을 흉내 낸 2분 뒤 **30가지 조건 모두** 좌우 움직임의 세로 휨이 커졌다(2~5% → 14~15%). 9/24 끄기로 결정하고 코드에서도 지움 |
| 렌즈 배럴 왜곡 되돌리기(k1) | 정규 얼굴이면 휨 절반, 얼굴이 다르면 **다섯 배 악화**. 가려낼 방법이 없어 9/3부터 꺼 둔 채였다 |
| 머리 자세 각도 매핑 | forehead.py 주석에 "**실제로 커서를 이 방식으로 움직여 본 적은 없다**". 상대 회전 매핑이 같은 문제를 푼다 |
| 입 오므리기 재정렬 | 오탐 때문에 7/30에 껐고 응시 재정렬로 대체됐다 |
| 조절 창의 감도·곡률 슬라이더 | 세 트래커가 상대 회전 매핑으로 바뀐 뒤 이 값은 **쓰이지 않는다.** 연구실 `eyebrow_tuning.json`에 곡률 −1.008이 저장돼 있었다 — 누군가 효과 없는 손잡이를 맞추느라 애쓴 흔적 |

조절 창을 고치다 **안내 문구가 "가로 각도" 슬라이더와 같은 줄에 겹쳐 그려지던 것**도 찾아
고쳤습니다(위젯 겹침 시험 추가).

**남긴 것**(측정으로 효과가 확인된 것): 고개 회전 방식(4~6배), 렌즈 자가 보정(3~7배), 1유로
필터(떨림 −31%), 클릭 붙잡기(드래그 방지), 거리 조절(옮긴 뒤 오차 13.4% → 0.5~2.5%), 목
가동범위 배려(41 → 90%), 응시 클릭.

**미룬 것 — 옛 2D 커서 방식.** 회전 방식의 캘리브레이션이 실패할 때만 타는 비상 경로라
실제로는 거의 안 탑니다. 지우면 세 파일의 감도·곡률 계수·점 평활 등 수백 줄과 시험 여럿을
뜯어야 해서 출시 직전보다 뒤가 안전합니다.

## 5. 시험이 다른 파이썬으로 돌고 있었다

exe들은 `py -3.11 head.py`처럼 폴더의 소스를 실행하는 얇은 실행기입니다. 그러니 오늘 고친
것은 exe를 다시 빌드하지 않아도 반영됩니다. 그런데 **제품은 파이썬 3.11로 도는데 시험은
3.13으로** 돌고 있었습니다.

| | 키오스크(`install.bat` → `requirements.txt`) | 이 PC의 3.11 | 시험을 돌리던 것 |
|---|---|---|---|
| 파이썬 | 3.11.5 | 3.11.5 | 3.13 |
| numpy | **1.26.4** | 2.2.6 | 2.4.4 |
| OpenCV | **4.10** | 5.0 | 5.0 |
| MediaPipe | 0.10.14 | 0.10.14 | 0.10.35 |

3.12부터 허용된 문법이 섞였으면 3.11에서는 **실행 자체가 안 됩니다.** 3.11로 전 파일을
컴파일했고(0건), numpy 2 전용 기능도 찾았습니다(0건). 그리고 E: 드라이브에 **키오스크와 같은
조합의 가상환경**을 만들어 시험 전체·스모크·장시간 실행을 다시 돌렸습니다
(E:/작업/_출시검증_py311, 프로젝트 폴더와 시스템 파이썬은 안 건드림).

### 옛 고정 버전(OpenCV 4.10)에서 렌즈 보정이 백 배 넘게 느렸다

그 환경에서 스모크 6가지와 12분 장시간 실행 3번은 통과했습니다. 그런데 **시험 전체가 29분이
지나도 끝나지 않았습니다.** 좁혀 보니 렌즈 자가 보정의 `cv2.calibrateCamera` 한 번이었습니다.

## 12. 렌즈 자가 보정이 발산하는 얼굴 — 기록만 남긴 것

전체 시험을 3.13에서 돌렸을 때 13분이 걸려(평소 4분) 들여다보니, 렌즈 보정 시험의 "눈 좁은
얼굴" 하나가 276초였습니다. 따라가 보니 두 가지가 겹쳐 있었습니다.

1. **정규 모형과 다른 얼굴에서는 보정이 발산한다.** 초점거리가 수백만 px로 가고(예: f=7,996,525),
   한 번에 0.1초대가 아니라 수 초씩 걸린 뒤 범위 밖으로 **거부**됩니다. 6번 시도하고 포기합니다 —
   안전장치는 제대로 일합니다(틀린 보정을 채택하지 않음).
2. **보정 스레드는 우선순위가 가장 낮아서** PC가 바쁘면 벽시계만 늘어납니다. 한 호출은 벽시계
   19.7초 동안 스레드 CPU를 0.5초만 썼습니다. 276초는 그때 PC가 바빴던 탓이고, 같은 시험을
   혼자 돌리면 28~32초였습니다. 커서를 막지 않으려고 일부러 그렇게 만든 것입니다.

얼굴 10종의 비용을 측정해 남겼습니다(`데이터 수치/lens_divergence.py` → `렌즈보정_발산.csv`, 출시 조합).

| 얼굴 | 시도 | 보정 CPU 합 | 결과 |
|---|---|---|---|
| 정규 모형 · 코 높은 · 갸름한 · 큰 얼굴 | 1번 | 0.6~1.4초 | 채택 |
| 눈 넓은 · 코 낮은 · 넓은 · 작은 얼굴(어린이) | 2~3번 | 1.8~4.3초 | 채택 |
| 겹친 최악 | 6번 | 5.3초 | 거부(시도 소진) |
| **눈 좁은 얼굴** | 6번 | **22.9초** | 거부(시도 소진) — 호출마다 발산 |

최악은 사람이 처음 나타났을 때 우선순위 가장 낮은 스레드가 CPU 한 코어를 23초쯤 쓰고 멈추는
것입니다. 발산이 보이면 일찍 그만두게 할 수 있지만, 가상 얼굴 10종만으로 "더 봐도 안 된다"를
말하기 어렵고 출시 직전에 검증된 보정 흐름을 바꾸는 위험이 더 크다고 봐 **고치지 않고 기록만**
남겼습니다(남은 것).

## 오늘 배운 것

**시험 도구도 시험해야 한다.** 장시간 실행의 빈 값은 트래커가 아니라 실행기가 확인할 기록을
지운 탓이었습니다. 실행기가 틀리면 멀쩡한 프로그램을 실패로 보고하고, 더 나쁘게는 30분을 돌려도
첫 40초만 확인하고 있었습니다. 원인은 추측하지 않고 이동 기록만 흘려 넣어 재현한 뒤 고쳤습니다.

**버그를 막는 일괄 수정도 버그를 만든다.** 8/28의 cp949 "구조적 차단"은 옳은 방향이었지만,
14개 파일에 넣은 뒤 하나씩 돌려 보지 않아 7개(빌드 도우미 6개와 `pipe_listen.py`)를 실행
불가로 만들었습니다. 일괄로 고칠 때는 고친 파일을 실제로 한 번씩 돌려 봐야 합니다. 그리고 그 일괄
수정의 시험은 print만 봐서, 도움말에서 같은 버그가 다섯 번째로 나왔습니다 — **글자를 세는 검사보다
실제로 돌려 보는 검사**가 빠뜨리는 게 적습니다.

**한 곳에서 찾은 원인은 같은 부류 전부에 넣어야 한다.** 첫 프레임 대기를 8/28에 측정
도구에서만 고쳐, 본체에서 같은 원인을 한 달 뒤 다시 만났습니다.

**꺼진 채 남은 기능도 비용이다.** 효과 없는 슬라이더는 누군가의 시간을 썼고, 꺼 둔 auto_arc
는 설정 파일을 읽는 측정 스크립트의 결과를 조용히 바꿀 수 있었습니다.

**시험 환경이 제품 환경과 다르면 통과가 아무것도 보장하지 않는다.** 파이썬도 numpy도
달랐습니다. 그리고 제품과 같은 조합으로 돌리자 비로소 OpenCV 4.10의 렌즈 보정 속도 문제가
드러났습니다 — 개발 PC에서는 보일 수 없던 문제입니다. 거꾸로, 설치 버전을 고칠 때는 키오스크에
까는 방식(휠 받기 → 통신 없이 설치) 그대로 다시 깔아 봐야 한다는 것도 이번에 절차로 남겼습니다.
