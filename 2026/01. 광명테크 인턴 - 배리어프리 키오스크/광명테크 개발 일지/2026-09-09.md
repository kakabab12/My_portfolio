# 2026-09-09 (화) 개발일지

노트북에서 테스트하다 두 가지가 걸렸습니다.

> "입 벌리면 커서 움직이고 아이콘에 커서 가져다 댈려고 하면 뭔가 흔들려.
>  그리고 커서가 파란색이 아닌데 드래그가 되는 현상이 있네."

증상은 둘인데 원인은 하나였습니다. 그리고 화면비 작업을 하다가, 세로
키오스크에서 겨냥이 통째로 틀어지는 것을 하나 더 찾았습니다.

테스트는 754개에서 **761개**로 늘었습니다.

## 1. 초록색인데 이미 눌려 있었다

8월 31일에 클릭 반응성 때문에 이렇게 바꿨습니다.

    입을 벌리는 순간          → mouse.press()   (버튼 DOWN)
    0.7초 넘게 벌리고 있으면  → 파란색으로 표시  (드래그)
    다물면                    → release

**그 0.7초 사이에 버튼은 눌려 있는데 커서는 초록색이고, 살아서 움직입니다.**
사용자가 본 두 증상이 정확히 여기서 나옵니다.

- 화면은 "안 눌림"인데 실제로는 드래그가 나갑니다 → *"파란색이 아닌데 드래그"*
- 입을 벌리느라 턱이 내려가면 얼굴 랜드마크가 밀리고, 커서가 그만큼 흘러갑니다
  → *"입 벌리면 커서가 움직인다"*

게다가 드래그용으로 넓혀 둔 데드존(`DRAG_DEAD_ZONE_SCALE`)도 `is_holding`이
켜져야 적용됩니다. **하필 그 0.7초 동안 데드존이 가장 좁습니다.**

### 고친 방법

세 가지를 함께 했습니다.

1. **눌린 순간 바로 파란색으로.** 보이는 색 = 실제 버튼 상태.
2. **눌린 뒤 드래그로 넘어가기 전까지 커서를 붙잡아 둡니다.** 짧은 벌림(클릭)은
   이제 **원리적으로** 커서를 못 움직입니다.
3. **붙잡는 지점은 지금 위치가 아니라 0.15초 전 위치입니다.** 입이 벌어졌다고
   판정될 무렵엔 이미 턱이 내려가 랜드마크가 밀린 뒤라, 지금 위치를 붙잡으면
   *밀려난 자리*를 붙잡게 됩니다. 그 직전이 사용자가 실제로 겨눈 곳입니다.

드래그로 넘어갈 때는 그냥 놓으면 커서가 튑니다 — 0.7초 동안 고개가 움직였을 수
있으니까요. 붙잡던 지점에서 현재 위치로 0.25초에 걸쳐 이어 줍니다.

`head.py` · `eyebrow.py` · `forehead.py` 세 군데 모두 같은 구조라 같이 고쳤습니다.

### 못 재는 것은 못 잰다고 적어 둡니다

입을 벌릴 때 강체 랜드마크가 얼마나 밀리는지는 **수치로 못 냈습니다.** 가상
카메라가 입 벌림에 따른 얼굴 변형을 모형화하지 않기 때문입니다(`데이터 수치/
00_README.md`의 "못 뽑은 것"에 이미 적혀 있습니다). 그래서 0.15초라는 값도
"임계값을 넘기까지 걸리는 시간"에서 온 어림이고, 임계값을 바꾸면 같이 봐야
한다고 코드 주석에 남겼습니다.

## 2. 화면비 — exe 6개, 엔진은 그대로 3개

> "3가지 버전 다 16:9 비율 버전 9:16 키오스크 버전 각각 이렇게 6개"

만들기 전에 **화면비에 따라 실제로 뭐가 달라지는지** 부터 봤습니다. 놀랍게도
하나뿐이었습니다.

| | 어디서 오나 | 화면비 따라 달라지나 |
|---|---|---|
| 커서 캔버스 | `GetSystemMetrics` 실제 해상도 | 이미 자동 |
| 겨냥 반폭 | EDID 실치수(mm) | 이미 자동 |
| 랜드마크 픽셀 척도 | 두 눈 사이 거리로 정규화 | 무관 |
| **카메라 프레임 크롭** | `config camera.portrait_crop` | **여기 하나** |

9:16 크롭은 1280×720의 중앙만 남겨 405×720을 만듭니다. 카메라를 물리적으로
돌리지 않고 세로 화면비를 맞추려고 넣은 것입니다. 가로 모니터에서 켜 두면
좌우 화각을 버리는 셈이라 몸이 옆으로 움직이면 얼굴이 프레임 밖으로 나갑니다.

크롭을 꺼도 **인식 정확도는 안 떨어집니다.** 높이를 안 건드리므로 얼굴이
차지하는 픽셀 크기가 그대로고, 추적은 두 눈 사이 거리로 정규화해 재기
때문입니다. 대신 추론 프레임이 405×720에서 1280×720으로 커집니다.

그래서 `--aspect {auto,kiosk,desktop}` 하나를 넣고, exe 6개가 그 값을 정해
주도록 했습니다. **1900줄짜리 엔진을 여섯 벌로 복사하지 않았습니다** — 오늘
클릭 버그 하나 고치는 데도 세 군데를 손댔는데, 여섯 벌이면 매번 여섯 군데입니다.

| 기준점 | 16:9 가로 | 9:16 세로 키오스크 |
|---|---|---|
| 코끝 | `head_16-9_데스크탑.exe` | `head_9-16_키오스크.exe` |
| 눈썹 | `eyebrow_16-9_데스크탑.exe` | `eyebrow_9-16_키오스크.exe` |
| 이마 | `forehead_16-9_데스크탑.exe` | `forehead_9-16_키오스크.exe` |

`make_aspect_exes.bat` 하나로 여섯 개를 임시 venv **하나에서** 만듭니다. 전부
표준 라이브러리만 쓰는 얇은 런처라 트래커별로 venv를 나눌 이유가 없었습니다.

## 3. 화면비를 확인하다 찾은 것 — 돌려 단 화면

"보정한 것들 각 화면비율에 맞게 다 조정한 거 맞냐"는 물음에 그렇다고 답하려다,
확인해 보고 **아니었다**는 것을 알았습니다.

`display_size.py`는 EDID에서 화면 실치수를 읽습니다. 그런데 **EDID는 패널이
원래 어떻게 생겼는지를 말합니다.** 가로형 32인치 패널을 벽에 세로로 돌려
달아도 EDID는 여전히 "597 × 336 mm"라고 답합니다. 하지만 사용자 앞의 화면은
336mm 폭에 597mm 높이입니다.

그대로 쓰면 겨냥 반폭의 가로·세로가 **통째로 뒤바뀝니다.**

| | 잘못 쓴 값 | 맞는 값 |
|---|---|---|
| 가로 반폭 (700mm 거리) | atan(298/700) = 23.1도 | atan(168/700) = **13.5도** |
| 세로 반폭 | atan(168/700) = 13.5도 | atan(298/700) = **23.1도** |

좌우는 필요한 것의 1.7배로 움직이고 위아래는 0.58배밖에 안 움직입니다.
**9:16 키오스크가 바로 이 배치입니다** — 고치지 않았으면 이번 작업의 요점이
정확히 거기서 무너질 뻔했습니다.

게다가 유효성 검사(`_sane`)가 세로 mm를 "말이 안 되는 값"으로 버리게 돼
있어서, 드라이버가 회전을 반영한 값을 줘도 통째로 버려졌습니다.

### 고친 방법 — 윈도우에 묻지 않고 픽셀과 대조

회전 설정을 API로 묻는 대신 **픽셀 해상도와 비교**합니다. 회전은 해상도에
그대로 나타나고(1080×1920), 실제 화면과 픽셀의 가로세로 방향은 반드시 같기
때문입니다. 화면 설정과 드라이버 중 **어느 쪽이 회전을 반영하고 어느 쪽이 안
하든** 이 대조는 성립합니다.

정사각형에 가까운 화면은 어느 쪽도 아니므로 손대지 않습니다 — 지어내지
않는다는 원칙 그대로입니다. 경로 전체(EDID → 검사 → 회전 보정)로 도는 것까지
테스트에 넣었습니다. 보정 함수만 만들어 놓고 부르는 것을 잊으면 조용히 틀린
채로 도니까요.

## 오늘 배운 것

**"다 맞췄냐"는 물음에 그렇다고 답하기 전에 확인해야 합니다.** 커서 캔버스도
겨냥 반폭도 이미 모니터를 직접 보고 정하니 화면비는 자동이라고 생각했는데,
"모니터를 직접 본다"는 그 경로 자체가 **패널이 원래 생긴 모양**을 보고
있었습니다. 자동화된 경로일수록 무엇을 근거로 자동인지 다시 봐야 합니다.

그리고 오늘 두 버그는 **보이는 상태와 실제 상태가 어긋나면 사용자가 그것을
두 가지 다른 증상으로 신고한다**는 예였습니다. "커서가 흔들린다"와 "파란색이
아닌데 드래그된다"는 완전히 다른 이야기처럼 들리지만, 색을 0.7초 늦게 켠
것 하나에서 둘 다 나왔습니다.
