# CPU로 실시간 깊이 추정 + 깊이 반응 조명

원본: Konrad Reczko가 TypeGPU(WebGPU)로 만든 데모 — 단안 이미지에서 AI로 깊이를
추정하고, 그 결과를 GPU 밖으로 꺼내지 않은 채 조명 계산·렌더링까지 command
encoder 하나로 이어서 처리. 448×448, M4 Pro에서 1회 8ms.

이 폴더는 같은 것을 **CPU에서** 해본 결과입니다.

## 질문: CPU로도 되나

**됩니다. 단, 원본이 자랑한 핵심 기법은 CPU에서 의미가 없어지고 다른 문제가 남습니다.**

원본의 자랑은 "GPU 밖으로 데이터를 안 꺼낸다"입니다. CPU에선 애초에 전부 같은
메모리에 있으므로 그 최적화 자체가 성립하지 않습니다. 남는 진짜 문제는 하나뿐입니다 —
**CPU가 깊이 추정 신경망을 얼마나 빨리 돌리느냐.**

측정 환경: Intel Core i5-10210U @1.6GHz (2019년 15W 4코어 노트북 CPU)

| | 원본 (M4 Pro GPU) | 이 PC (CPU) |
|---|---|---|
| 깊이 추정 1회 | 8ms @ 448×448 | **70~120ms @ 256×256** |
| 처리 구조 | 순차 (한 encoder) | **분리** (아래 설명) |
| 화면 | 60fps | **24~26fps** |
| 깊이 갱신 | 60fps | **8~9fps** |

448×448은 이 CPU로 323ms(3fps)라 불가능합니다. 256×256이 현실적인 상한입니다.

## 구조가 원본과 다른 이유

원본은 깊이 추정이 8ms라 한 프레임(16ms) 안에 추론→조명→렌더가 다 끝납니다.
CPU는 추정 하나에 100ms가 걸려서, 똑같이 순차로 이으면 **카메라 영상 전체가
그 속도로 떨어져** 뚝뚝 끊깁니다.

그래서 깊이 추정만 따로 떼어 자기 속도로 돌린다:

- 화면과 조명은 카메라 속도(25fps)로 매끄럽게 계속 돌고
- 깊이 맵은 준비되는 대로(8~9fps) 갈아 끼웁니다

깊이는 몇 프레임 묵어도 잘 티가 안 나는 정보인 반면, 영상이 끊기는 건 바로
보인다 — 그 차이를 이용한 거랩니다. `--sync`를 주면 원본처럼 순차 처리해서 두
방식을 직접 비교할 수 있습니다.

## 측정하면서 뒤집힌 예상 3가지

**1. 스레드는 논리 코어 수만큼 주면 안 된다**

    intra_op 1개 149ms · 2개 100ms · 4개 69ms · 8개 114ms

이 CPU는 물리 4코어 + 하이퍼스레딩 8논리코어인데, 8로 맞추면 **오히려 60% 느려집니다.**
하이퍼스레딩으로 늘어난 논리 코어는 연산 유닛을 공유하므로, 이런 순수 계산
작업에서는 서로 방해만 합니다. **물리 코어 수**에 맞추는 게 맞습니다.

**2. INT8 양자화가 3.5배 느려졌다**

    FP32 71.6ms  →  INT8 252.6ms   (모델 크기는 66.8MB → 17.3MB로 줄었는데도)

INT8은 "무조건 빠르다"가 아닙니다. CPU에 VNNI 명령어가 있어야 가속되는데,
i5-10210U(Comet Lake, 2019)에는 없습니다. 없으면 느린 우회 경로로 돌면서 매 실행마다
양자화·역양자화 비용까지 더해집니다. VNNI는 Ice Lake(2019 후반) 이후 CPU에 들어갔습니다.

**3. 조명 해상도는 작을수록 좋은 게 아니다**

    256×256 17.8ms · 160×160 12.3ms · 128×128 11.7ms · 96×96 17.1ms

작게 계산할수록 연산은 줄지만 화면 크기로 늘리는 비용이 커져서, 어느 지점부터
손해로 뒤집힙니다. 128이 골짜기 바닥이라 그 값을 씁니다.


## 조사해서 반영한 것 (2026-08-21)

이 분야에서 이미 검증된 기법을 찾아 적용했습니다. 전부 실측으로 효과를 확인했습니다.

### ① 깊이 흔들림 제거 — 시간 평활

MiDaS 같은 모델은 **affine-invariant depth**를 냅니다. 원근의 순서는 맞지만 스케일과
오프셋이 매 프레임 제멋대로라, 정지한 장면인데도 깊이가 미세하게 떨립니다.

    실제 카메라 40프레임(정지 장면) — 프레임 간 평균 변화
      안정화 없음   0.03509
      시간 평활     0.00954      -> 떨림 3.7배 감소
    반응 지연: 3프레임 (깊이 8fps 기준 0.38초)

**★ scale-shift 정렬은 넣었다가 뺐다 — 검증에서 걸렸습니다.**

논문들이 쓰는 기법이라 그대로 옮겼다(새 깊이를 직전 프레임에 최소제곱으로 맞추기).
그런데 검증해보니 정규화 잡음만이 아니라 **진짜 움직임까지 맞춰서 없애버렸다**:

    사람이 깊이 0.5 -> 0.9로 다가왔을 때 (40프레임)
      정렬 켬:  0.500 -> 0.500   전혀 안 따라옴. 못 씁니다
      정렬 끔:  0.500 -> 0.900   정상

    같은 장면 500프레임 (값이 흘러가는지)
      정렬 켬:  0.684 -> 0.379   오차가 누적돼 슬금슬금 흘러감
      정렬 끔:  0.701 -> 0.702   안정

논문들은 전체 구간을 공통 기준에 맞추거나(co-alignment) 정적인 영역만 골라 쓰는데,
직전 프레임 하나에 그냥 맞추면 이렇게 됩니다. 기법을 이름만 보고 가져오면 안 된다는
사례로 남겨둡니다 — 코드는 남아 있지만 기본은 꺼져 있습니다.

### ② 경계 정렬 — Guided Filter (He et al. 2010)

깊이는 뭉툭하게 나와서 그냥 늘리면 사람 윤곽이 흐물거리고 조명이 얼굴 밖으로
새어 나갑니다. 컬러 영상을 길잡이로 삼아 늘리면 경계가 실제 윤곽에 붙습니다.

비용을 44배 줄인 두 가지:

    컬러 길잡이 640x480    30.8ms
    흑백 길잡이 640x480    12.2ms   <- 채널 수가 비용의 대부분이었습니다
    조명 해상도(128)에서만   0.7ms   <- 채택 (조명을 어차피 128에서 계산합니다)

### ③ 빛나는 구체의 가림 처리

처음엔 구체를 깊이 무시하고 맨 위에 덧그렸습니다. 그래서 광원을 머리 뒤로 옮겨도
구체가 얼굴 위에 떠 있었다 — 조명은 "뒤에서 비추는" 계산을 하는데 구체만 앞에
보이니 장면 속의 빛이 아니라 화면에 붙인 스티커처럼 보였습니다. 이제 그 자리의
물체가 광원보다 가까우면 구체를 가립니다.

    실측: 앞에 물체가 들어오면 구체 밝기 255 -> 9

### ④ 자동 깊이 — 가리킨 표면에 빛을 놓습니다

광원을 **가리킨 표면 바로 앞**(0.06)에 자동으로 놓습니다. 벽을 가리키면 빛이 벽에
가서 붙고, 그 앞으로 손이나 얼굴을 내밀면 빛이 가려져 사라집니다. 빛이 화면에
붙은 게 아니라 방 안 한 자리에 놓여 있다는 느낌이 여기서 나옵니다.

이건 ①을 하고 나서야 가능해졌습니다. 그전엔 매 프레임 다시 정규화돼서 "장면 속
고정된 깊이"라는 개념 자체가 성립하지 않았습니다.

### ⑤ 광원이 물체를 피해 도망가던 버그

자동 깊이를 처음 만들 때 **매 프레임** 커서 자리의 깊이를 다시 읽었습니다. 그러면
손을 광원 앞으로 가져가는 순간 광원이 **손 앞으로 도망가서**, "가까이 가면 빛이
가려진다"가 영원히 일어나지 않습니다. 빛이 물체를 피해 다니니 장면 안에 놓인 게
아니라 커서에 붙어 다니는 꼴이었습니다.

빛은 **놓아둔 자리에 머물러야** 가려질 수 있습니다. 그래서 깊이를 정하는 건 끌고
있는 동안뿐이고, 손을 떼면 그 깊이에 고정됩니다.

    실측(일반 웹캠): 배경에 빛을 놓고 앞으로 물체를 가져갈 때
      광원 z    0.93 -> 0.93 -> 0.93 -> 0.93   (안 움직입니다)
      구체 밝기  255 ->   19 ->   19 ->   19   (가려집니다)

### ⑥ 실루엣에 생기던 밝은 테두리

사람 윤곽처럼 깊이가 뚝 끊기는 자리는 기울기가 폭발해서 "거의 수직으로 선 벽"
으로 계산됩니다. 그런 면은 옆에서 오는 빛을 정면으로 받아 얇고 밝은 테두리를
만든다 — 실제로는 벽이 아니라 그냥 물체의 가장자리인데도. 표면 기울기에 현실적인
상한(`max_slope`)을 둬서 잘라냈습니다. 코·볼 같은 완만한 굴곡은 그대로 살아 있습니다.

## 구체가 안 숨을 때 (사용법)

"손을 가까이 가져가면 구체가 뒤로 숨는" 동작이 안 보인다면, 십중팔구 **광원이
장면 맨 앞에 있어서** 아무것도 그 앞을 가로막을 수 없는 상태입니다.

화면 왼쪽 위 표시를 보면 바로 알 수 있다:

    light z 0.91   surface here 0.35   HIDDEN behind object
           ↑ 광원 거리        ↑ 그 자리 물체 거리      ↑ 지금 가려짐

  · `light z`가 작을수록 카메라에 가깝습니다. 0.35보다 작으면 장면 맨 앞이라
    **절대 안 숨는다** — 휠을 아래로 굴려 뒤로 보내거나, 벽을 드래그해 놓으면 됩니다.
  · `surface here`가 `light z`보다 작아지는 순간 = 뭔가 광원 앞에 온 순간 = 숨습니다.

**제대로 보려면**: 사람이 없는 벽을 드래그해서 빛을 놓는다(z가 0.9 근처가 됩니다)
→ 그 앞으로 손을 내민다 → 손이 밝아지면서 구체가 손 뒤로 사라집니다.

광원은 **놓아둔 자리에 머문다**. 그래야 가려질 수 있기 때문입니다 — 매 프레임 커서
아래 표면을 따라가게 만들었더니 손이 다가오면 광원이 손 앞으로 도망가서 영원히
안 숨었다(그 버그는 고쳤습니다).

## 파일

| 파일 | 하는 일 |
|---|---|
| `main.py` | 본체 — 카메라 → 깊이 → 조명 → 화면 |
| `depth_model.py` | MiDaS v2.1 small (ONNX) 래퍼 |
| `depth_lighting.py` | 깊이 → 표면 법선 → 조명. 단독 실행하면 모델 없이 자체 검증 |
| `make_sample.py` | [원본 \| 깊이 \| 조명] 3단 비교 이미지 생성 |
| `depth_stabilizer.py` | 깊이 흔들림 제거 + 경계 정렬. 단독 실행하면 효과 측정 |
| `bench_feasibility.py` | 모델 없이 "이 CPU로 될지"만 미리 재보는 도구 |

## 실행

```bash
py -3.11 main.py                    # 기본 (분리 방식)
py -3.11 main.py --sync             # 원본과 같은 순차 방식으로 비교
py -3.11 main.py --threads 4        # 깊이 추정 스레드 수 지정
py -3.11 make_sample.py             # 3단 비교 이미지 저장
py -3.11 depth_lighting.py          # 조명 단계만 자체 검증 (모델 불필요)
```

조작: `q`/`ESC` 종료 · `d` 깊이맵 보기 · `l` 조명 끄기 · `space` 광원 회전 멈춤


## 왜 내 얼굴은 안 밝아지나 (실측으로 밝혀낸 것)

원본 데모처럼 만들었는데 얼굴이 계속 어두웠습니다. 조명 수식을 한참 의심했지만
**조명은 처음부터 제대로 돌고 있었다** — 사람이 배경보다 1.8배 많은 빛을 받고
있었습니다. 진짜 원인은 입력이었다:

    원본 프레임 밝기   얼굴 15~47 / 255      흰 벽 124~192 / 255   (최대 8.6배 차이)

흰 벽을 등지고 앉으면 카메라가 벽에 노출을 맞춰서 얼굴이 거의 안 담깁니다.
정보가 없는 걸 빛으로 키울 수는 없다 — 극단적인 설정까지 훑어봐도 사람이 배경봅니다
1.15배 밝아지는 게 한계였습니다.

카메라 노출로 고치려 했지만 **이 Brio 100은 노출 제어가 안 먹는다**(실측:
`set()`이 True를 반환하는데 값이 안 바뀌고 그림도 그대로, BRIGHTNESS는 아예 False).

증거: 같은 코드에 **잘 노출된 사진**을 넣으면 원본 데모와 똑같은 그림이 나옵니다
(`ref_relit.png`). 코드가 아니라 입력의 문제였습니다.

**해결 순서**
1. 흰 벽을 등지지 말 것 / 얼굴 쪽에 불을 켤 것 — 가장 확실합니다
2. 그게 안 되면 `--relight` (역광 보정). 입력에 구워진 조명을 걷어냅니다.
   실측으로 8.6배 차이가 2.4배까지 줄지만 근본 해결은 아닙니다.

## 한계

- 입력이 256×256 고정이다(이 ONNX가 동적 크기를 지원하지 않습니다). 더 낮춰서
  속도를 벌 수 없습니다.
- 깊이는 **상대적인 원근**이지 미터 단위 거리가 아닙니다. 조명에는 충분하지만
  거리 측정 용도로는 못 씁니다.
- 이 노트북 CPU는 15W라 오래 돌리면 발열 제한이 걸린다 — 같은 설정에서
  70ms~160ms까지 흔들립니다. 위 수치는 지속 부하 기준입니다.
- 더 빠르게 하려면 결국 GPU입니다. 이 PC에 외장 GPU가 있다면 onnxruntime-directml로
  바꾸는 것만으로 원본에 가까운 속도가 나올 가능성이 높습니다.
