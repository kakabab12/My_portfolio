# gesture_kiosk — 제스처 인식 배리어프리 민원발급기 (추론)

(주)광명테크 인턴 프로젝트. USB 카메라 1대로 제스처를 실시간 인식해
키오스크 프로그램으로 이벤트를 전달한다. **기획서(기획서.docx)의
2.3 디렉터리 구조와 4장 코딩 컨벤션을 따른다.**

- 실행 환경: **윈도우 + Python 3.11.5 — CPU 단독** (정부 민원발급기):
  2026-07-29 포즈 스택 제거로 GPU·CUDA 불필요 (구 GPU 자동 감지 통합판은 07-24~07-29)
- 동작 체계(2026-07-23 — 「제스처 정의 보고서」 손 모양 기준, 회사 확정):
  **손 모양이 계층을, 이동 방향이 기능을 정한다** — 한 손가락=탐색, 주먹=명령
- 모델: **MediaPipe HandLandmarker(Apache-2.0) 단일** — 내장 TFLite(XNNPACK) CPU 추론.
  손 21점(화면+월드 3D)으로 모양 판별·궤적·사용자 선별·거리 자까지 전부 판정
  (2026-07-29 포즈(rtmlib/ONNX Runtime) 제거 — 손 모양 판별은 자체 기하 규칙, 별도 CNN 없음)
- 연동: **파이프(stdio)** — 이벤트를 stdout에 한 줄씩 print, 델파이7 UI가 파이프로
  수신 (2026-07-23 회사 확정 — 네트워크(UDP·웹소켓) 전면 철회)
- 학습(파인튜닝)은 별도 `training/` 폴더 담당 (feat/study 브랜치) — 이 폴더는 추론 전용

## 처리 흐름

```
카메라(스레드) → 거울 반전 → 손 랜드마크(MediaPipe HandLandmarker — 주 추론 모델)
  → 사용자 손 선별(hand_select: 머리 앵커 게이트 + 단일 손 추적, 손 실측 거리 자)
  → 손 모양(hand_shape: 주먹/한 손가락/손바닥) → 동작 판정(gesture_filter:
     모양 래치 + 첫 선 궤적 + 탭) → 이벤트 print(stdio)
  ※머리 앵커(포즈)는 별도 스레드에서 초당 10회 — 손 루프 비차단
```

### 상대 회전 매핑 — 카메라를 어떻게 달아도 된다 (2026-08-31 ~ 09-03)

예전에는 세 방식 모두 **화면에 투영된 2D 좌표**로 커서를 정했다. 코처럼
얼굴에서 튀어나온 점은 고개를 돌리면 원근 때문에 비선형으로 움직여서,
좌우로만 돌려도 세로가 활처럼 휘었다. 이를 2차식(`ARC_COMPENSATION`)으로
사후 보정했는데, 그 계수는 **카메라 배치가 바뀌면 다시 측정해야 했다.**

지금은 **중립 자세 대비 상대 회전**으로 커서를 정한다
(`src/postprocess/head_orientation.py`). 시작할 때 잡은 중립과 지금 프레임의
강체 랜드마크 22개를 Kabsch-Umeyama로 맞춰 회전을 구하고, 그것을
**회전벡터로 분해**해 좌우·상하를 뽑는다.

카메라 배치가 상쇄되는 이유는 간단하다 — 카메라를 M만큼 기울여 달면 두
시점 모두에 M이 곱해지고, 상대 회전에서 서로 나뉘며 사라진다.

    R_상대 = (M·R_지금)·(M·R_중립)ᵀ = M·R_지금·R_중립ᵀ·Mᵀ

**세 진입점 전부 기본으로 켜져 있다**(`ORIENTATION_MAPPING = True`).
`configs/config.yaml`의 `orientation_mapping`도 2026-09-03에 `true`로
바꿔 `main.py` 계열까지 같은 경로를 쓴다. 켜지면 `sensitivity_x/y`와
`arc_compensation`은 함께 무시된다 — 각도로 직접 매핑해서 둘 다 필요 없다.

**검증** — 가상 카메라(`tests/virtual_camera.py`)로 관측을 합성해 전수 확인했다.

- 배치 9종 × 거울 ON/OFF **288/288**, 밑에서 0~80도 각 16/16
- 렌즈 5종(왜곡없음~초광각 120도) × 배치 9종에서 커서 방향 전부 통과
- 몸이 옆으로 움직여도 커서가 따라가지 않음(끌림 한도 0.020)

### 렌즈 자가 보정 (2026-09-03)

광각 카메라의 **배럴 왜곡**과 **원근 단축**을 사용자의 얼굴을 보정판 삼아
되돌린다(`src/postprocess/lens_calibration.py`). 현장에서 아무것도 측정하지 않고,
증거가 부족하면 스스로 아무것도 하지 않는다.

- 초점거리를 알아내 원근을 되돌린다 → 몸 평행이동 끌림 0.036~0.042 → 0.006~0.017
- 배럴 왜곡 되돌리기는 **기본 꺼짐** — 얼굴이 정규 모형과 다르면 해로운데
  그것을 가려낼 잡음-독립적 지표를 찾지 못했다(2026-09-24 선택지째 삭제)
- 자세한 근거는 `docs/PAPERS.md`

### 설치할 때 한 번 — 거리 하나만 (2026-09-05)

커서가 **얼굴이 향한 곳**에 있으려면 화면 절반 폭에 닿는 각도를 알아야 한다.
그 값은 고르는 것이 아니라 기하학이 정한다.

    반폭 = atan((화면 가로 / 2) / 사용자와의 거리)

화면 크기는 **운영체제가 모니터에서 읽어 온다**(`src/utils/display_size.py`).
픽셀 해상도로는 알 수 없다 — 1920×1080이 14인치일 수도 55인치일 수도 있고
물리 크기는 4배 차이다. 그래서 설치할 때 정할 것은 **거리 하나**다.

```yaml
# configs/config.yaml  ->  head_tracker.pointer
reference_distance_mm: 800    # 데스크탑(앉아서) 500~700, 키오스크(서서) 700~1000
```

- 줄자로 한 번 측정하는 것이 가장 정확하다. 카메라로 추정해 봤으나 초점거리가
  얼굴 생김새에 따라 중앙값 15.7%·최악 69.3%까지 틀려 **섞을수록 나빠졌다**
- 넣지 않으면(null) 이 경로가 꺼지고 예전 각도(15도)를 그대로 쓴다
- 사용자가 앞뒤로 움직이는 것은 얼굴 크기 비로 따라간다(오차 0.7%)
- 효과: 얼굴이 향한 점과 커서의 어긋남 평균 6.4% → **3.1%**, 최악 20.0% → **11.0%**

**고개가 조금밖에 안 돌아가는 사용자**는 화면 가장자리에 못 닿는다
(좌우 7도면 화면 폭의 45.8%까지). 그 사람의 실제 가동범위를 재서 권장값을
알려 주는 도구가 있다 — 자동으로 정하지 않는 이유도 함께 알려 준다.

```bash
py scripts/measure_reach.py
```

### 화면비 — 16:9 데스크탑과 9:16 키오스크 한 벌로 (2026-09-09)

```bash
py forehead.py --aspect desktop   # 16:9 가로
py forehead.py --aspect kiosk     # 9:16 세로
py forehead.py                    # auto — 화면 해상도를 보고 결정
```

화면비에 따라 실제로 달라지는 것은 **카메라 프레임 크롭 하나뿐**이다. 커서
캔버스는 실제 해상도를, 화면 끝을 보는 고개 각도은 EDID 실치수를, 랜드마크 척도는 두 눈
사이 거리를 이미 직접 보고 정한다. 그래서 파일을 화면비별로 나누지 않았다.

**세로로 돌려 단 화면 주의** — EDID는 패널이 *원래 생긴 모양*을 말한다.
가로형 패널을 세로로 달아도 "597×336 mm"라고 답하는데 실제 화면은 336×597이라,
그대로 쓰면 화면 끝을 보는 고개 각도의 가로·세로가 뒤바뀐다(700 mm에서 23.1도 ↔ 13.5도).
윈도우 회전 설정을 묻지 않고 **픽셀 해상도와 대조**해 바로잡는다. 자세한
것은 `화면비_exe_안내.md`.

### 클릭·드래그 — 가상 사용자로 확인한다 (2026-09-10)

입을 벌리는 **순간** 버튼이 눌린다(반응성). 짧게 벌렸다 다물면 클릭(노란
깜빡임), 계속 벌리고 있으면 드래그(파란 커서)다. 판정은
`src/postprocess/mouth_gesture.py`에 있고 세 진입점이 함께 쓴다.

누르는 동안에는 **커서를 붙잡는다.** 안 그러면 입을 벌리느라 얼굴이 밀린
만큼 커서가 흘러가고, 버튼이 이미 눌려 있으므로 그 흘러감이 곧 의도치 않은
드래그가 된다.

이 판정은 테스트에서 두 번 어긋났고 두 번 다 짐작으로 고쳤다가, 두 번째
보고가 첫 번째 수정 때문에 생긴 일이었다. 그래서 판정을 모듈로 꺼내고
**가상 사용자가 실제 파이프라인으로 직접 써 보게** 했다
(`tests/virtual_user.py`, `tests/test_virtual_user_click.py`). 사람은 클릭
도중에도 고개를 움직이고 입을 매번 같은 깊이로 다물지 않으므로, 시나리오에
그것이 들어 있다.

그렇게 찾은 결함 둘:

- **다물어도 클릭이 안 되던 것.** 다묾 선이 기준선+0.05인데 사람은 클릭 뒤
  입을 완전히 안 다문다. 턱이 0.11에 머무르면 영영 안 내려와서 → 클릭 실패
  → 0.7초 뒤 드래그 → 드래그 해제는 더 빡빡해 역시 실패 → **버튼이 눌린 채
  남았다.** "얼마나 벌렸었나에 견주어" 판단하도록 고쳤다.
- **되짚기가 곧 드래그였던 것.** 밀림을 되돌리려고 조금 이전 위치를 붙잡았는데,
  보정이 버튼이 내려간 뒤에 일어나 그만큼 그대로 끌렸다. 되짚은 거리와 끌린
  거리가 일대일이라 되짚기를 뺐다(얼굴이 향한 곳과 커서 사이 거리 12~25 px, 끌림 0 px. 붙잡기를
  아예 끄면 오차 25~264 px에 끌림 63~242 px).

## 출시 전 점검 (2026-09-25)

출시할 때마다 아래 셋을 **키오스크와 같은 버전 조합**(파이썬 3.11.5 +
`requirements.txt` 고정 버전 — numpy 2.2.6, OpenCV 5.0.0.93, MediaPipe 0.10.14)에서
돌린다. 개발 PC의 파이썬이 다르면 통과해도 키오스크에서 죽을 수 있다.

실제로 한 번 달랐다. 9월 25일까지 고정 버전은 numpy 1.26.4 + OpenCV 4.10이었는데
개발 PC는 5.0이었다. 고정 버전 조합에서 전체 시험이 29분이 지나도 끝나지 않아
찾아보니, 렌즈 자가 보정 한 번(`cv2.calibrateCamera`)이 4.10에서 수십 초였다
(5.0은 0.1초대, 결과는 같음). 켠 뒤 그만큼 보정이 늦게 적용되고 그동안 CPU를
붙잡으므로 고정 버전을 5.0 조합으로 올렸다
(`데이터 수치/lens_speed.py` → `렌즈보정_속도.csv`).

| 명령 | 무엇을 보나 |
|---|---|
| `py -m pytest tests -q` | 판정·매핑 모듈과 스모크 실행기 자체 961건. 실행 스크립트 전부에서 정의 없이 쓰이는 이름과 import보다 먼저 쓰는 이름(`tests/test_script_names.py`), 파이프·cp949에서 `--help`가 죽는 스크립트(`tests/test_entry_help.py`)도 잡는다 |
| `py tests\tracker_smoke.py all` | 세 트래커 × 두 화면비의 `main()`을 가상 카메라·가상 사용자로 **처음부터 끝까지** 돌린다(약 45초). 안내대로 8초 대기 → 좌우 가리키기 → 클릭 3번 → 드래그 → 얼굴이 2초 사라짐 → 다시 나타나 클릭 → 옆에 다른 사람. 마우스·창·카메라만 가짜이고 나머지는 진짜 코드다 |
| `py tests\tracker_smoke.py head --soak 60` | 같은 흐름을 60분 되풀이하며 메모리 추세와 스레드 수가 늘지 않는지, **오래 켠 뒤에도** 커서가 맞는지(위치 확인을 첫 회차와 마지막 회차에서 모두) 본다 |

스모크 실행기는 시작 점검을 그대로 거치므로 얼굴 모델 파일이 있어야 한다
(새로 받은 저장소라면 먼저 `py scripts\download_weights.py`).

테스트가 판정 모듈을 따로 보는 것만으로는 부족했다. 2026-09-10에 `main()` 안쪽의
정의 두 개가 리팩터 중에 지워졌는데 컴파일·자가 점검·테스트가 모두 통과했고,
사용자가 실행한 뒤에야 드러났다. 스모크 실행기는 그 구간을 실제로 돈다.

그래도 **사람이 쓰는 확인을 대신하지는 못한다.** 입을 벌릴 때 얼굴이 변형되는 것,
실제 조명과 카메라, 사람의 입 동작 속도는 가상 사용자에 없다. 실제 키오스크에서의
확인 항목은 개발 일지 2026-09-25에 있다.
