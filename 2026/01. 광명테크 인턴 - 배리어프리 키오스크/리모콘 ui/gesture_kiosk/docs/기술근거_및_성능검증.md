# 헤드트래커 입력장치 — 기술 근거 및 성능 검증 체계

배리어프리 키오스크용 비접촉 입력장치(헤드트래커)의 기술적 근거와 성능을
어떻게 검증하는지 정리한 문서. 조달·심사 제출 시 기술 설명 자료로 쓰는 것을
전제로, **출처가 확인된 것만** 적었습니다.

작성 2026-08-27

---

## 1. 무엇을 만들었나

손을 쓰기 어려운 사용자가 **고개 움직임과 입 벌리기만으로** 민원발급 키오스크를
조작할 수 있게 하는 입력장치. 기존 키오스크에 **USB 카메라 1대만 추가**하면
동작하며, 별도 그래픽카드·깊이센서·전용 하드웨어가 필요 없습니다.

| 동작 | 기능 |
|---|---|
| 고개 움직임 | 커서 이동 |
| 입 벌렸다 닫기 | 클릭 |
| 빠르게 두 번 | 더블클릭 |
| 입 벌린 채 유지 | 끌기(드래그) |
| 1.5초 응시 | 클릭 (입을 쓰기 어려운 사용자용 대체 경로) |

### 제도적 배경

「장애인차별금지 및 권리구제 등에 관한 법률」에 따른 **배리어프리 키오스크
설치·운영 의무가 2026년 1월 28일부터 전면 시행** 중입니다. 관련 국가표준은
**KS X 9211:2022 「무인정보단말기 접근성 지침」**(2022-02-25 개정)입니다.

> ⚠ KS X 9211 원문은 유료 표준이라 이 문서 작성 시점에 조항별 수치(버튼 크기·
> 조작 시간 한계 등)를 확인하지 못했습니다. **제출 전 e나라표준인증 또는
> 한국표준정보망에서 원문을 받아 조항 대조를 반드시 거칠 것.** 이 문서는
> 조항 번호를 인용하지 않는다 — 확인하지 않은 것을 인용하지 않기 위해서입니다.

## 2. 성능을 어떻게 증명하는가 — ISO 9241-411

### 왜 이 표준인가

"성공률 90%"라는 숫자만으로는 심사위원이 **마우스보다 나은지** 알 수 없습니다.
ISO 9241-411은 마우스·트랙볼·터치·시선추적을 **같은 잣대 하나로** 비교하도록
국제적으로 합의된 절차이고, 그 잣대가 **처리량(Throughput, bit/s)** 입니다.

> ISO 9241-411:2012 (2022 재확인) — 비키보드 입력장치의 인간 성능 평가 시험.
> 6가지 과제 중 이 프로젝트는 **다방향 탭 시험(multi-directional tapping)** 을 씁니다.

### 계산식

```
처리량  TP  = IDe / MT            (bit/s)
난이도  IDe = log2(Ae / We + 1)   (bit)
유효폭  We  = 4.133 × SD(dx)
유효거리 Ae  = 명목거리 + 평균편차
```

- `dx` = 클릭 지점이 과녁 중심에서 **이동 축 방향으로** 얼마나 빗나갔는지
  (MacKenzie의 표준 사영식 — 세 변의 길이만으로 계산)
- `4.133` = 정규분포 ±2.066 표준편차, 전체의 **96%** 에 해당

### 이 표준이 조작 못 하게 막는 것

처리량은 **"대충 빨리 찍기"로 올릴 수 없습니다.** 산포가 커지면 `We`가 커지고
`IDe`가 깎여 자동으로 상쇄되기 때문입니다. 이 성질을 실제로 검증했다:

```
신중하게: 산포 SD 10.7px → IDe 1.706 bit / 1.00초 → TP 1.706 bit/s
대충 빨리: 산포 SD 21.4px → IDe 1.092 bit / 0.50초 → TP 2.184 bit/s
           └ 시간을 절반으로 줄여도 난이도가 0.614 bit 깎여 보정됨
```

즉 **속도-정확도 상충이 표준 안에서 자동 정산**됩니다. 이래서 심사 자료로서
신뢰성이 있습니다.

### 비교 기준값

같은 표준 절차로 측정된 공개 문헌값 (HMD 환경 Fitts 법칙 비교 연구):

| 입력 방식 | 처리량 |
|---|---|
| 마우스 | 2.75 bit/s |
| **머리 조작** | **2.04 bit/s** ← 이 프로젝트와 같은 범주 |
| 시선 조작 | 1.85 bit/s |

> 장비·과제가 달라 절대 비교는 조심해야 하지만, 같은 표준 절차라 **자릿수
> 비교는 유효**합니다.

### 측정 도구

`scripts/measure_throughput_iso.py` — 과녁 13개를 원형 배치하고 반대편으로
건너뛰며 탭하는 표준 절차를 그대로 구현했습니다. 거리×크기 조합 5가지를 돌려
조건별 처리량과 **Fitts 회귀선(MT = a + b·IDe, R²)** 까지 냅니다.

```bash
py forehead.py                              # 트래커 실행
py scripts/measure_throughput_iso.py --label forehead   # 측정
```

**수식 검증 완료** — 손으로 계산한 값과 소수점 이하까지 대조했다:
사영 편차 4케이스 · 처리량 계산 · 속도-정확도 상쇄 · Fitts 회귀 계수 복원.

> ⚠ **현재 상태: 계측 도구는 완성·검증됐으나 실제 측정값은 아직 없습니다.**
> 사람이 직접 시험해야 나오는 숫자입니다. 제출 전 반드시 측정할 것.

## 3. 적용한 기술과 근거

### 3.1 커서 떨림 저감 — 1€ 필터

> Casiez, G., Roussel, N., Vogel, D. **"1€ Filter: A Simple Speed-based
> Low-pass Filter for Noisy Input in Interactive Systems."** ACM CHI 2012.

마우스·터치·머리추적 등 실시간 포인팅 인터페이스의 떨림 제거에 널리 쓰이는
알고리즘. 속도를 함께 추정해 **정지 시에는 강하게 평활(떨림 제거), 빠르게
움직일 때는 평활을 풀어(지연 최소화)** 둘을 동시에 만족시킵니다.

단순 EMA 하나로는 이 둘을 동시에 만족할 수 없다 — 이 프로젝트가 그동안 감도
상수 여러 개를 손으로 절충해 온 문제 자체를 알고리즘이 대신 풉니다.

**검증**: 정지 입력 드리프트 0 · 정지 잡음 40% 이상 저감 · 빠른 램프 추종 확인
(`tests/test_cursor_smoothing.py`)

### 3.2 거리 적응 평활 — 자체 실측 기반

**문제**: 사용자가 카메라에서 멀수록 커서가 더 떨립니다. 실측값:

| 안구간거리 | 커서 흔들림 | 곱 |
|---|---|---|
| 90px (가까움) | 2.0px | 180 |
| 60px (키오스크) | 3.0px | 180 |
| 40px (물러섬) | 4.5px | 180 |

**곱이 정확히 일정** — 즉 흔들림이 1/거리에 정비례합니다. 커서 위치를
`(랜드마크 이동 px ÷ 안구간거리)`로 정하는데 랜드마크 잡음 자체는 거리와
무관하게 일정하니, 나누는 값이 작아질수록(멀수록) 같은 잡음이 그대로 증폭됩니다.

**대응**: 평활 강도를 거리에 비례시켜 이 증폭을 정확히 상쇄합니다.

**검증 결과** (시뮬레이션, `tests/test_cursor_smoothing.py`):

| 안구간거리 | 적응 OFF | 적응 ON | 변화 |
|---|---|---|---|
| 90px (가까움) | 17.4px | 17.4px | **동일** |
| 60px (기준) | 26.1px | 26.1px | **동일** |
| 40px (물러섬) | 39.1px | 31.8px | **18.6% 개선** |
| 30px (많이 물러섬) | 52.1px | 36.1px | **30.6% 개선** |

> 설계 결정: 배율 상한을 1.0으로 묶었습니다. 처음 2.0으로 뒀더니 가까운 사용자가
> 오히려 21% 더 떨렸다 — 반응성을 얻는 대신 검증된 감각을 깨뜨리는 건 손해라고
> 판단했습니다. **"같거나 나아지기만 한다"** 를 보장합니다.

### 3.3 저조도 대응 — CLAHE

> Zuiderveld, K. **"Contrast Limited Adaptive Histogram Equalization."**
> Graphics Gems IV, Academic Press, 1994.

일반 히스토그램 평활화는 영상 전체 명암을 넓게 펴서 어두운 영역의 **잡음까지
증폭**시킵니다. CLAHE는 화면을 타일로 나눠 국소적으로, **대비 상한을 두고** 폅니다.

**적용 설계**
- 밝을 때는 **아예 건드리지 않음** — 이미 잘 보이는 영상에 대비를 더 올리면
  부작용만 생깁니다
- **인식용 프레임에만** 적용 — 화면에 보이는 색감은 그대로
- **Y(밝기) 채널에만** 적용 — 색 왜곡 방지

**성능**: 밝기 판정을 32×32 축소본으로 먼저 걸러, 밝을 때(대부분의 시간)
**0.016ms — 사실상 무비용**. 실제로 어두울 때만 전체 처리(~8ms)를 냅니다.

**실기 확인**: 조명을 끈 상태에서 인식 정상 동작 확인.

### 3.4 조작자 특정 — 뒷사람 방어

동사무소·법원처럼 **줄을 서는 곳**에 놓이는 장치라, 뒤나 옆 사람에게 조작권이
넘어가면 제품이 성립하지 않습니다. 깊이센서 없이 RGB 카메라만으로 해결해야 했습니다.

앵커 고정 → 크기 기반 거리 추정 → 팔 길이 제약 → **배경 흐림 처리**(인식
모델에게 다른 사람을 아예 안 보여줌)까지 순차 적용해 실사용 수준에 도달했습니다.

### 3.5 무인 운영 안정성

관리자가 상주하지 않는 장비에서 가장 나쁜 실패는 "꺼지는 것"이 아니라
**조용히 멈추는 것**입니다. 화면은 멀쩡한데 반응만 없으면 사용자는 자기 탓인 줄
알고 돌아갑니다.

| 장치 | 내용 |
|---|---|
| 카메라 자동 복구 | 드라이버 예외·USB 탈락 시 4초 내 자동 재연결 |
| 감시 장치 | 추론 정지 / 카메라 신호 없음을 구분해 화면에 안내 |
| 로그 폭주 방지 | 오류 40초치 약 1,200건 → **2줄**, 파일 20MB 상한 |
| 종료 안전장치 | 예외·Ctrl+C·창 닫기 전부에서 마우스 커서·버튼 복구 |
| 출력 차단 대응 | 표준출력이 막혀도 추론이 멈추지 않음 |
| 시작 자가 점검 | 설정·모델·카메라를 미리 확인하고 해결법까지 안내 |

| OpenCV | Apache-2.0 | **가능** |
| NumPy | BSD-3-Clause | **가능** |
| PyYAML | MIT | **가능** |

| Pillow | MIT-CMU | **가능** |
| PyInstaller (빌드 도구) | GPL v2 + 예외 | **가능** — 예외 조항으로 빌드 결과물은 GPL 비적용 |

초기에 검토했던 AGPL 계열(ultralytics, HaGRID YOLOv10)은 **2026-07-10에
전부 제거**했습니다.

> 배포물에 각 라이선스 고지문을 동봉하는 것은 통상 절차다(제품 화면 표시
> 의무는 없습니다). **제출 전 사내 법무 검토를 한 번 더 거칠 것** — 이 표는
> 일반적인 라이선스 조항 기준 정리이며 법률 자문이 아니다.

## 6. 제출 전 반드시 할 일

1. **ISO 처리량 실측** — `scripts/measure_throughput_iso.py` 실행.
   가능하면 여러 명(고령자·장애 유형별 포함)에게 시험해 평균과 편차를 낼 것.
   숫자가 하나라도 나오면 심사 자료의 무게가 완전히 달라집니다.
2. **KS X 9211:2022 원문 확보 후 조항 대조** — e나라표준인증(무료 열람) 또는
   한국표준정보망.
3. **사내 법무 라이선스 검토**.
4. 비교 대상(마우스·터치)을 같은 도구로 함께 측정하면 설득력이 더 커집니다.
