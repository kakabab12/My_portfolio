### 발생한 문제와 해결

**문제 1 — `mp.solutions` 없음**

```
AttributeError: module 'mediapipe' has no attribute 'solutions'
```

설치된 mediapipe 0.10.35에서 legacy `solutions` API가 제거됨.
→ **Tasks API로 전면 재작성.** `PoseLandmarker` / `HandLandmarker` 사용, `.task` 모델 파일 별도 다운로드.

**문제 2 — 한글 경로에서 모델 로딩 실패**

```
RuntimeError: Unable to open file at C:\Users\지용\...\pose_landmarker_lite.task, errno=-1
```

MediaPipe의 C++ 로더가 non-ASCII 경로를 못 엶.
→ `model_asset_path` 대신 **파일을 바이트로 읽어 `model_asset_buffer`로 전달.**

**문제 3 — `cv2.imshow` 창이 안 뜸**

```
cv2.error: The function is not implemented. Rebuild the library with Windows, GTK+ 2.x or Cocoa support
```

`lerobot`이 `opencv-python-headless`를 함께 설치하는데, 이게 GUI 빌드를 가림.
→ headless 제거 후 **`opencv-contrib-python` 재설치.**

**문제 4 — 모터 6개 전부 무응답 (가장 오래 걸린 문제)**

| 진단 | 결과 |
| --- | --- |
| COM3 포트 열림 | 정상 |
| 프로토콜 0·1 × 보드레이트 6종 × ID 0~20 스캔 | **0개 발견** |
| 브로드캐스트 ping raw 전송 | **0바이트 응답** (에코조차 없음) |

→ **원인: 12V 전원 잭 접촉 불량.**
USB만 꽂아도 보드는 인식되고 빨간 LED도 켜지기 때문에 전원 문제인지 구분이 안 됐다.
잭을 다시 체결하니 6개 전부 즉시 인식.

> **판별법 정리**: USB를 뽑은 상태에서 LED가 계속 켜져 있으면 12V 정상.
> 꺼지면 12V가 안 들어오는 것. COM 포트 인식 여부는 판단 기준이 될 수 없다.

**문제 5 — lerobot 모듈 경로 변경**

`lerobot` 0.4.4에서 `so101_follower` → `so_follower`로 이름 변경.
→ try/except로 양쪽 지원.

## 오후 — 매핑 정교화

### 좌표계 문제 해결

| 문제 | 원인 | 해결 |
| --- | --- | --- |
| 몸통이 화면 밖이면 계산 불가 | 어깨–엉덩이 길이로 정규화 | **위팔 길이(어깨–팔꿈치)로 변경** |
| pan/lift가 서로 섞임 | 어깨 각도를 하나로 계산 | 좌우(x)·상하(y)로 **분리** |
| 좌우 방향 판별 불안정 | 하드코딩 | **반대쪽 어깨 위치로 자동 판별** |

### 방향 반전 문제 (반복 발생)

방향이 반대로 나오는 관절이 계속 나타남. 매번 프로그램을 껐다 켜며 확인하는 게 비효율적이라
**실행 중 키보드로 즉시 반전**할 수 있게 개선.

| 관절 | 최종 상태 |
| --- | --- |
| shoulder_pan | 반전 필요 |
| shoulder_lift | 반전 필요 |
| elbow_flex | 정방향 |
| wrist_flex | 정방향 (부호있는 각도로 수정 후) |
| gripper | 정방향 |

**중요한 교훈** — 반전을 넣었다 뺐다 반복한 이유:
`wrist_flex`가 **부호 없는 각도**(0~180°)를 쓰고 있어서 위로 꺾으나 아래로 꺾으나
"구부러진 정도"만 나왔다. 방향 자체를 구분 못 하는 상태에서 반전을 켜니 계속 어긋났다.
→ **외적 기반 부호 있는 각도**로 교체하니 해결.

### 1:1 각도 매핑으로 전환

"내가 45도 들면 로봇도 45도"가 목표. `remap`으로 범위를 늘려 잡던 걸 전부 실제 각도로 변경.

| 관절 | 이전 | 이후 |
| --- | --- | --- |
| shoulder_lift | 비율(sin값) → ±100 | `asin`으로 **실제 각도 복원** |
| elbow_flex | remap 압축 단위 | `180° − 안쪽각` |
| wrist_flex | remap ±80 → ±100 | 측정 각도 그대로 |

**문제 — "팔을 다 펴도 로봇은 절반만 펴짐"**

두 가지가 겹쳐 있었다.

1. `JOINT_LIMITS`가 ±100°로 자름 → 팔꿈치는 최대 150°까지 굽는데 잘려나감
2. 1:1 전환하면서 **0점이 100도 어긋남** → 로봇의 0도는 캘리브레이션 중간 위치인데
   사람의 "쭉 편 상태"를 0도로 계산

**진단 근거**: 모터 3번의 마지막 `Goal_Position`이 3867 = 정확히 상한 160°에 박혀 있었다.
(모터 자체는 정상: ping OK, 온도 36°C, 에러 0)

→ `--elbow-offset` 기본값 −100, `JOINT_LIMITS` 확대(`elbow_flex`: −110~160).

### 감도 문제

**"크게 움직여야만 반응함"** — 배율 문제인 줄 알았으나 실제 주범은
**1€ 필터가 느린 움직임을 잡음으로 판단해 눌러버린 것**이었다.

| 파라미터 | 이전 | 이후 |
| --- | --- | --- |
| `min-cutoff` | 1.0 | 2.5 |
| `beta` | 0.4 | 0.6 |
| `smooth-time` | 0.15 | 0.10 |
| `max-speed` | 150 | 200 |
| `gain` (신규) | — | 1.8 |

이후 **"많이 움직이되 빠르지 않게"** 요청으로 배율↑ / 속도↓ 재조정
(`max-speed` 90, `smooth-time` 0.22).

**포화(saturation) 문제** — `shoulder_lift`에 오프셋 +35~50이 남아 있어
배율 2.0배와 겹치면 **팔을 38도만 올려도 상한 110°에 도달**. 그 이상 안 움직임.
→ 배율과 오프셋의 트레이드오프를 수치로 제시하고 조정.

### 실행 중 튜닝 시스템 구축

껐다 켜는 반복을 없애기 위해 키보드 조작 추가.

| 키 | 기능 |
| --- | --- |
| `1`~`6` | 관절 선택 |
| `[` / `]` | 선택 관절 0점 −5 / +5도 |
| `-` / `=` | 전체 배율 −0.2 / +0.2 |
| `,` / `.` | 선택 관절만 배율 조정 |
| `i` | 방향 반전 |
| `c` | 깊이 중립 재설정 |
| `w` | **`tuning.json`에 저장** (다음 실행부터 자동 적용) |
| `p` | 현재 설정 출력 |
| `s` | 스냅샷 저장 |
| `q`/ESC | 종료 |

`tuning.json`은 임시 파일에 쓴 뒤 교체하여 저장 중 중단돼도 기존 설정이 깨지지 않게 처리.

# 2026-08-29 (2일차)

## 3D 전환 — 가장 큰 구조 변경

### 문제

**"팔을 정면으로 보이게 하면 관절값을 잘 못 읽는다"**

2D 투영의 원리적 한계. 팔이 카메라를 향하면 화면상 길이가 줄어들어(foreshortening)
각도가 뭉개진다. 팔꿈치를 90도 굽히고 정면으로 뻗으면 화면엔 거의 직선으로 보인다.
**필터나 배율로는 절대 해결 불가.**

### 해결 — world landmark + 몸통 기준 좌표계

MediaPipe가 `pose_world_landmarks`로 **미터 단위 3D 좌표**를 이미 제공하고 있었다
(초기 "xy만" 요구사항 때문에 사용하지 않고 있었음).

여기에 **몸통 직교 기저**를 구성:

| 축 | 정의 |
| --- | --- |
| `u_lat` | 어깨선 (좌우) |
| `u_up` | 척추, 그람-슈미트로 직교화 (상하) |
| `u_fwd` | `u_lat × u_up` (정면) |

팔 벡터를 이 기저에 투영 → **카메라 위치·몸 방향과 무관한 각도**.

### 검증 (팔꿈치 90도 고정, 방향만 변경)

| 위팔 방향 | elbow_flex |
| --- | --- |
| 옆으로 | 90° |
| **정면(카메라쪽)** | **90°** |
| 앞+옆 45도 | 90° |
| 위/아래 | 90° |

전 방향에서 정확히 90°. 2D였으면 정면에서 무너졌을 값.

## 조도 대응

### LightingNormalizer (CLAHE + 적응형 감마)

LAB 색공간의 **L(밝기) 채널에만** 적용. 색은 건드리지 않아 피부색 기반 검출을 해치지 않음.

- **CLAHE** (Zuiderveld 1994) — 타일 단위 국소 대비 향상, 역광·그림자 대응
- **적응형 감마** — 전역 밝기를 목표치(125)로 유도

| 조건 | 원본 밝기 | 보정 후 | 원본 대비 | 보정 대비 |
| --- | --- | --- | --- | --- |
| 정상 | 124.5 | 122.0 | 55.0 | 49.8 |
| 어두움 | 30.8 | **77.2** | 13.8 | 20.1 |
| 매우 어두움 | 14.5 | **62.2** | 6.6 | 13.5 |
| 과노출 | 211.4 | **183.9** | 60.4 | 88.5 |

화면 표시용 영상은 원본 유지, **추론용 이미지에만** 적용.

> **작업 중 버그**: 감마 지수가 뒤집혀 어두운 영상을 더 어둡게(30.8 → 12.3) 만들고 있었음.
> `(i/255)^(1/gamma)` → `(i/255)^exponent`로 수정.

## 그리퍼 정확도 개선

### 문제

손끝 사이 거리로 주먹을 판정 → 손을 옆으로 돌리면 투영으로 거리가 줄어 **주먹으로 오인**.

### 해결 — 3D 손가락 관절각

마디 사이 각도의 합을 사용. 손의 크기·거리·회전과 무관.
네 손가락 중 **중앙 2개 평균**을 취해 이상치에 강하게 처리.

| 손 상태 | gripper | 0°/45°/90° 회전 편차 |
| --- | --- | --- |
| 완전히 폄 | 100 | **0.0** |
| 반쯤 | 50 | **0.0** |
| 주먹 | 15 | **0.0** |

> **작업 중 발견한 실제 버그**: `remap()`이 **입력 범위가 내림차순일 때 항상 0을 반환**.
> 가드가 `in_hi - in_lo < 1e-9`인데 음수도 걸림 → `abs()`로 수정.
> 새 그리퍼 코드가 이걸 밟아 값이 계속 100으로 나와 발견.

## 정확도 개선 — 뼈 길이 제약 (핵심 성과)

### 진단

정지 상태에서 15초간 측정:

| 항목 | 평균 | 표준편차 | 변동폭 | 변동률 |
| --- | --- | --- | --- | --- |
| 위팔 길이 | 0.212 m | 0.016 | 0.068 | **7.7%** |
| 아래팔 길이 | 0.199 m | 0.010 | 0.065 | **5.2%** |
| 팔꿈치각 | 78.6° | 7.55° | 37.4° | 9.6% |

**뼈는 물리적으로 길이가 변하지 않는다.** 이 7.7%는 전부 추정 오차.

### 해법 — 깊이를 역산

관찰:
- 이미지 평면의 x, y → **정확함**
- 깊이 z → **부정확함**
- 뼈 길이는 **불변**

따라서 z를 추정값으로 쓰지 않고 피타고라스로 역산:

```
dz = ±√(L² − dx² − dy²)
```

부호(앞/뒤)만 MediaPipe의 z에서 가져옴 (크기는 못 믿어도 부호는 신뢰 가능).
픽셀 → 미터 변환은 **어깨너비를 자로** 사용.

뼈 길이는 시작 후 45프레임의 **중앙값**으로 자동 캘리브레이션 (이상치에 강함).

### 검증 결과 (필터 영향 배제, A/B 측정)

| 관절 | 보정 OFF | 보정 ON | 개선 |
| --- | --- | --- | --- |
| shoulder_pan | 10.03° | **2.26°** | **78%** |
| shoulder_lift | 7.67° | **3.30°** | **57%** |
| elbow_flex | 7.18° | **3.74°** | **48%** |

## 남은 한계

- **`wrist_roll`** — 단안 2D로는 전완 길이방향 회전을 원리적으로 관측 불가
- **가려짐** — 팔이 몸에 완전히 가려지면 어떤 알고리즘도 복원 불가
- **깊이 모호성** — 좌우 대칭 자세에서 원리적 모호성 잔존
- **프레임레이트** — 웹캠 하드웨어 상한 15 FPS

정확도 100%는 단안 카메라로 달성 불가능하나, 위 개선으로 실사용에는 충분한 수준.
