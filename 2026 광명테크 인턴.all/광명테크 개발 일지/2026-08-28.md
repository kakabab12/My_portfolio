## 2. forehead.py 곡률 보정 — 진짜 버그를 찾다

### 2-1. 5차 — 첫 실측치 적용

`measure_arc.py`로 처음 실측: 표본 800개, 곡률 +1.1029(R²=0.825, 화면
좌우 끝에서 +27.6% 처짐). 부호를 뒤집어 `ARC_COMPENSATION = -1.1029` 적용,
forehead.exe 재빌드.

재검증을 두 번 더 돌렸는데 곡률이 -0.27, -0.358로 나왔다(R²=0.19~0.22로
낮음). "신뢰도가 낮다"고 판단해 그 자리에선 보류했다 — **이게 실수였다.**

### 2-2. 실사용 보고로 드러난 진짜 원인

사용자가 실제로 켜서 써보고 정확히 짚었다 — "여전히 U 모양이고, 화면 끝
쪽에서 커서가 위로 올라간다." 그리고 "좌우로 움직일 때 약간 눕힌 S자
느낌"까지.

코드를 다시 보니 진짜 버그가 있었다(`src/postprocess/head_tracker.py`):

```python
# 수정 전
if self._arc_compensation:
    offset_y += self._arc_compensation * offset_x * offset_x
offset_x = _clamp(offset_x, self._max_offset_ratio)
```

보정을 **클램프 전(raw)** offset_x로 계산했다. 커서가 이미 화면 가장자리에
닿은 뒤에도 고개를 더 돌리면, 화면에 보이는 커서 위치는 안 바뀌어도 raw
offset_x는 계속 커지고, 그 제곱에 비례하는 보정량도 한없이 커진다 —
결국 offset_y가 보정만으로 자기 클램프에 부딪혀 "화면 끝에서 커서가 위로
확 올라간다"가 나오고, 중간 구간의 잔여 곡률과 겹쳐 "누운 S자"로 보였다.

이게 곧 재측정 두 번이 들쭉날쭉했던 이유이기도 하다 — **낮은 R²가 "잡음이니
무시해도 된다"는 뜻이 아니라, 매 세션마다 머리를 얼마나 더 멀리 돌렸는지에
따라 이 폭주량 자체가 달라졌다는 뜻이었다.**

**고침**:

```python
# 수정 후
if self._arc_compensation:
    clamped_offset_x = _clamp(offset_x, self._max_offset_ratio)
    offset_y += self._arc_compensation * clamped_offset_x * clamped_offset_x
offset_x = _clamp(offset_x, self._max_offset_ratio)
```

화면에서 가장 많이 휘는 지점은 정확히 커서가 가장자리에 닿는 지점(offset_x가
클램프에 닿는 지점)이다 — 그 이상 고개를 돌려도 커서 표시 위치는 안
바뀌므로 보정도 그 이상 커질 이유가 없다.

**회귀 테스트 추가** (`tests/test_cursor_smoothing.py`) —
`test_compensation_does_not_run_away_past_the_clamp`: 클램프를 훌쩍 넘는
두 dx(10px, 30px)를 넣었을 때 결과가 완전히 같은지 확인. 수정 전 코드로
돌리면 실패(-0.161 vs -0.5), 수정 후엔 통과(-0.075 vs -0.075)함을 사전에
직접 계산해 검증한 뒤 작성했다.

### 2-3. 6차 — 세 측정치를 조합해 재계산

앞서 "잡음"이라 버렸던 두 측정치도 실은 실제 신호였으므로, 세 값을 전부
살려서 다시 계산했다. "결과곡률 = 원래곡률 + 보정값" 관계로 역산:

| 측정 | 보정값 | 관측 곡률 | 역산한 "원래곡률" |
|---|---|---|---|
| 1차 | 0 | +1.1029 | 1.1029 |
| 2차 | -1.1029 | -0.27 | 0.8329 |
| 3차 | -1.1029 | -0.358 | 0.7449 |

평균 0.8936 → `ARC_COMPENSATION = -0.8936` 적용, forehead.exe 재빌드.
추측이 아니라 이미 잰 값 3개를 조합한 결과다.

## 5. eyebrow.py 눈 깜빡임 커서 흔들림 — 세 번 만에 잡다

**증상** — "눈 깜빡일 때 커서가 아래로 흔들린다"(감도 6.0으로 올린 뒤 두드러짐).

### 1차 — 중앙값 필터 (부족)

미간 기준점이 정확히 "두 눈 바깥쪽 끝의 중점"이라, 눈을 깜빡이는 순간
눈가 근육 수축으로 이 랜드마크가 1~2프레임 흔들리면 그 잡음이 감도 6배로
그대로 증폭된다. head_tracker.py의 `_median()`이 이미 문서화해 둔 원칙
("눈 깜빡임 같은 순간적 이상치는 평균 대신 중앙값으로 거른다")을 매 프레임
흐르는 신호에 상시 적용 — `_RollingMedianPoint`(최근 5프레임 중앙값) 신설.

재보고: "여전히 눈감을때 커서가 내려가더라." **부족했다** — 중앙값은
"창의 절반 이상이 정상"일 때만 이상치를 거르는데, 눈을 감고 있는 동안
내내(수백 ms) 낮게 잡히는 건 중앙값 입장에선 "이상치"가 아니라 "다수"가
되기 때문이다.

### 2차 — 더 위 단계에서 차단 (여전히 부족)

`_glabella_point`에서 점 좌표만 얼리는 방식으로 재설계했는데도 여전했다.
원인을 다시 보니 `HeadTracker.update()`가 안구간거리(`_smoothed_dist_px`)를
`cursor_point_fn`과는 **완전히 별도로** face에서 직접 다시 읽고 있었다
(head_tracker.py 670~671행). eyebrow.py는 `dx = (좌표차이) /
_smoothed_dist_px`로 나누는 방식이라, 분자(미간 좌표)를 아무리 얼려도
분모(안구간거리)가 눈 깜빡임 중 살짝만 흔들리면 결과가 같이 흔들린다 —
**점 하나만 얼리는 걸로는 이 경로를 못 막는다.**

그래서 더 위 단계로 옮겼다 — 눈을 감은 동안은 `head_tracker.update()`
**호출 자체를 건너뛰고** 직전 결과를 재사용(`_BlinkGate`, `_process_one_frame`).
호출을 아예 안 하므로 분자든 분모든 내부 상태가 전부 통째로 멈췄다가, 눈을
뜨면 멈춘 지점에서 그대로 이어간다.

재보고: "여전해, 전보다 덜할 뿐." 방향은 맞았지만 완전하지 않았다.

### 3차 — 히스테리시스 + 쿨다운 (해결)

진입 문턱 하나만으론 실제 깜빡임의 "램프"(눈꺼풀이 서서히 감기고 뜨이는
구간)를 못 잡는다 — 반쯤 감기고/반쯤 뜨이는 몇 프레임은 문턱 아래라 그대로
통과해 흔들림이 샜다. 정확히 "감고 뜨는 전환 순간"이라는 보고와 일치한다.

04_참고_논문_기술.md에 이미 정리해 둔 원칙("히스테리시스 + 쿨다운" — 입
벌림 등 다른 판정에도 쓰는 방식)을 그대로 적용:

- **진입 문턱**(0.15) — 이 이상 튀면 "감기 시작"
- **해제 문턱**(0.05, 진입보다 낮음) — 완전히 평상시 근처로 가라앉아야
  "다 떴다"고 보고 얼림을 푼다 (덜 뜬 채로 너무 일찍 안 풀리게)
- **최소 유지 시간**(0.08초) — 한 번 얼면 최소 이 시간은 무조건 유지
  (짧은 흔들림에 바로 안 풀리게)

고정 임계값을 안 쓰는 이유는 head_tracker.py의 "home"(양눈 감고 버티기)
판정과 같다 — 사람마다 평상시 eyeBlink 점수가 0.1~0.6까지 벌어져서, 고정
값 하나면 어떤 사람은 커서가 아예 안 움직이는 오탐이 날 수 있다. 각자의
평상시 점수를 천천히 따라가며 마진 이상 튀었을 때만 판정한다.

테스트 9개(`tests/test_eyebrow_glabella.py`) — 첫 프레임 오탐 방지, 지속
깜빡임 감지, 정상 복귀, 평상시 점수 높은 사용자 오탐 방지, **램프 구간에서
너무 일찍 안 풀리는지**, 최소 유지 시간 준수. 전체 315개 테스트 통과.

> **오늘의 교훈 하나** — "덜할 뿐"이라는 재보고를 가볍게 넘기지 않고 정확한
> 재현 조건("감고 **뜰 때**")을 다시 물어본 게 세 번째 시도에서 진짜 원인
> (전환 램프)을 찾은 열쇠였다.

## 6. eyebrow.py 곡률 보정 — 카메라 각도 독립적 해법

사용자가 스스로 원인을 정확히 짚었다 — "우리 키오스크는 카메라가 정면,
연구실은 아래에서 위로 보고 있어서 그런 것 같다. 카메라 각도·위치에
상관없이 수정해야 하지 않을까."

**정확한 지적이다** — 이 휨의 원인(미간이 회전축보다 카메라 쪽으로 살짝
튀어나와 있어 고개를 돌리면 원근으로 세로까지 밀리는 것) 자체가 카메라가
얼굴을 어디서 보고 있느냐에 따라 다르게 투영된다. **하나의 공식으로 모든
카메라 배치에 맞는 계수는 없다.**

그래서 forehead.py 때 이미 만든 클램프 버그 수정(2번 항목)이 적용된
`ARC_COMPENSATION` 훅을 eyebrow.py에도 새로 추가하고 — "카메라 각도
독립적인 해법"은 공식이 아니라 **그 자리에서 measure_arc.py로 직접 재는
것** 자체라고 안내했다. 이 도구는 화면에 실제로 나타나는 커서 궤적만
재므로 카메라가 어디 있든 그 배치에 필요한 값을 그대로 알려준다.

연구실에서 measure_arc.py를 몇 차례 돌렸는데 R²가 낮게 나와(중앙값 필터·
블링크 게이트 개발과 겹쳐 순수하게 좌우로만 왕복하기 까다로웠던 것으로
보임) 최종적으로는 **실사용 중 직접 시험**해 `-0.7` → `-0.75`로 확정했다.
forehead.py 때와 달리 정밀 R² 측정을 거치진 않았지만, 실제 사용 중 확인이
가장 확실한 검증이라 이 값을 그대로 썼다.

## 7. eyebrow.py 버벅거림 — 1€ 필터 신규 적용

**증상** — "좀 버벅거리는게 있어 커서가 프레임 문제인거같은데."

eyebrow.py는 지금까지 고정 세기 EMA 평활만 썼다. 감도를 6.0까지 올리자
카메라 프레임마다 있는 아주 작은 위치 흔들림도 그만큼 증폭돼 그대로

눌러서 오히려 늦게 따라오는 두 문제를 동시에 겪는 구조다("버벅거림"으로
느껴진 게 이것으로 추정).

forehead.py에서 이미 검증한 **1€ 필터**(속도를 같이 봐서 가만히 있을 땐
세게, 빠르게 움직일 땐 풀어주는 방식)를 그대로 켰다 — `ONE_EURO_ENABLED`
등 forehead.py에서 실기로 맞춘 값을 시작점으로 가져왔다. 다만 두 파일의
감도 조합이 다르므로(forehead X=2.8·Y=3.8 vs eyebrow X=2.05·Y=6.0) 최적값은
다를 수 있어 실기로 다시 다듬어야 할 수 있다.

## 8. 실시간 감도·곡률 조절 UI — 볼륨 조절 방식

사용자 아이디어 — "메뉴얼 만들까 아니면 UI로 만들까... 볼륨 조절처럼 그냥
만들어 버리자." 코드를 고쳐서 값을 바꿀 때마다 재빌드·재배포해야 했던
지금까지의 방식(감도·`ARC_COMPENSATION` 등) 대신, 슬라이더로 그 자리에서
바로 맞추고 확인할 수 있게 만들었다.

**구조** — UI(`scripts/tuning_ui.py`, Tkinter, 새 의존성 없음)와 트래커는
같은 프로세스가 아니라 **작은 JSON 파일 하나로만** 이어진다.

```
슬라이더 조작 -> JSON 파일에 즉시 저장
                 -> 트래커가 0.5초마다 파일 수정 시각만 확인
                    -> 바뀌었으면 다시 읽어 head_tracker에 반영
```

이 구조 하나로 사용자가 요구한 두 조건이 자연히 풀린다:
- **실시간 반영** — 다음 확인 주기(최대 0.5초)에 알아서 반영
- **UI를 꺼도 유지** — 값이 파일에 남아 있어 창을 닫아도, 트래커를
  재시작해도 마지막 값 그대로 시작한다

또 "언제 UI가 나오면 좋겠냐"는 질문에는 **항상 떠 있는 방식이 아니라
콘솔에 `tune`+Enter를 쳤을 때만** 뜨게 했다 — 이 프로그램은 키오스크
운영자가 보는 화면이라, 평소엔 조작 창 하나 없이 깨끗해야 한다는 이
프로젝트의 기존 원칙(콘솔 명령 `p`/`quit`/`cam on`/`cam off`)과 같은
방식을 그대로 따른 것이다.

**공용 코드에 작은 훅 추가** — `head_tracker.py`에
`_CursorMapper.set_tuning()` / `HeadTracker.set_pointer_tuning()`을
새로 만들었다. 캘리브레이션 상태는 전혀 안 건드리고 감도·곡률 보정 값만
바꿔서, 슬라이더를 움직이는 순간 커서가 순간이동하듯 튀지 않는다.

**테스트 과정에서 또 버그 하나 잡음** — `_TuningReloader`의 "마지막으로
확인한 시각"을 `0.0`으로 초기화했는데, 테스트용 가짜 시계가 마침 `0.0`에서
시작하다 보니 **첫 확인 자체가 통째로 건너뛰어지는** 게 드러났다. 실제
`time.monotonic()`은 0 근처일 일이 거의 없어 실기에선 안 드러났을 문제다
— `-inf`로 고쳐 첫 확인이 항상 되게 했다. eyebrow.py·forehead.py 양쪽에
같은 클래스를 복제해 넣었는데, forehead.py 쪽 테스트에도 **똑같이 이
회귀를 재현하는 테스트**를 넣어 같은 실수가 반복되지 않게 했다.

테스트 15개 신규, 전체 330개 통과. eyebrow.exe·forehead.exe 재빌드, 실제
창이 뜨는 것까지 확인 후 GitHub에 반영.

## 오늘의 교훈

**"신뢰도가 낮다"와 "신호가 아니다"는 다르다.** 2번 항목에서 R²가 낮다고
두 측정치를 버렸는데, 그 값들이 사실은 실제로 존재하는 폭주 버그를 정확히
가리키고 있었다. 통계적 신뢰도가 낮다는 건 "이 숫자 하나를 그대로 믿지
말라"는 뜻이지 "이 현상 자체를 무시하라"는 뜻이 아니다 — 실사용 보고와
같이 놓고 봤어야 더 빨리 원인을 찾았을 것이다.

**"고쳤다"는 사용자가 확인해야 끝난다.** 5번 항목의 눈 깜빡임 문제는
겉보기엔 그럴듯한 수정(중앙값 필터, 그다음 상위 단계 차단)을 두 번이나
내놓았지만 둘 다 실사용에서는 부족했다. 그때마다 사용자가 "여전히", "덜할
뿐"이라고 정확하게 다시 알려준 덕분에 세 번째에 진짜 원인(전환 램프)을
잡을 수 있었다 — 단위테스트가 통과한다고 실기에서 끝난 게 아니다.

**같은 원칙이 파일을 넘나들며 재사용됐다.** 히스테리시스+쿨다운(6번),
1€ 필터(7번), 클램프 버그 수정(2번, head_tracker.py 공용 코드라 eyebrow.py
곡률 보정에도 자동으로 적용됨) — 전부 forehead.py나 다른 판정에서 이미
검증해 둔 것을 그대로 가져왔다. 새로 설계하지 않고 이미 있는 걸 재사용한
덕분에 세 가지 다 큰 사고 없이 한 번에 자리 잡았다.

**가짜 시계로 짠 테스트가 실제 환경에서는 안 드러날 버그를 잡아냈다**
(8번). `time.monotonic()`을 그대로 썼다면 이 초기화 버그는 아마 배포 후
한참 뒤, 어쩌다 프로세스가 부팅 직후처럼 시계가 0에 가까운 드문 상황에서만
터졌을 것이다 — 테스트를 "그럴듯하게 통과시키는" 게 아니라 경계값(0.0
근처)을 의도적으로 짚어보는 습관이 실제로 값어치를 했다.
